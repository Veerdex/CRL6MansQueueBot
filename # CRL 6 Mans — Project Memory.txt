# CRL 6 Mans — Project Memory

Discord bot + companion website for a small, high-skill (Champ+) Rocket League community running 3v3 6-mans pickup games. This file is the durable source of truth for game mechanics and architecture direction — read it in full before working on any phase of this project.

Source docs (original spec + Q&A) live at `C:\Users\grant\Downloads\CRL 6 Mans Queue Bot\` (`6mans_bot_spec.md`, `Extra Context.txt`, `claude_code_prompt.md`). This file supersedes them where they conflict — see "Resolved clarifications" below.

## Architecture direction

- **Website**: Next.js on **Vercel**.
- **Database**: **Supabase** (Postgres) — shared source of truth for both the website and the Discord bot. Not SQLite (original spec assumed a bot-local SQLite file; superseded).
- **Discord bot**: **not** a separate process — it's a set of Next.js API routes living inside `web/`, deployed as part of the same Vercel project as the website. Decided this session: every bot feature (queue buttons, vote/draft buttons, slash commands) is Discord-interaction-triggered, and Discord supports an **HTTP Interactions Endpoint** model (Discord POSTs each interaction to a webhook URL) as an alternative to a persistent gateway/WebSocket connection — this fits Vercel's serverless model with no extra hosting platform needed. See "Discord bot runtime architecture" below for the concrete mechanics (signature verification, the 3-second response limit, background sweeps via Supabase `pg_cron`).
- **Build approach**: incremental, one piece at a time. Each phase gets a brainstorm/design discussion *before* implementation — never build ahead of an agreed design.

## Game mechanics (resolved design)

### Queueing
- **Universal Queue** (open to all ranks) and **Rank Queue** (open to everyone immediately, regardless of placement — see "Bands / ranks" below) both exist.
- **Universal Queue is fully unranked**: results there never change MMR. Only Rank Queue series run the Elo update. This is a deliberate deviation from the original spec doc (which assumed one MMR shared symmetrically by both queues) — decided this session.
- Universal Queue games still count toward general games-played counters (season eligibility, lifetime `total_games_played`) and still display against a player's current MMR for context — they just never move it. **Not** the placement counter (revised this session — see "Placement" below): placement assigns a real band off MMR, and Universal games never move MMR, so only Rank Queue games count toward `placement_games_required`.
- A player may sit in both queues simultaneously. If one pops (6/6), auto-remove them from the other queue and notify (DM or channel ping).
- No auto-fallback/forced merging — a queue that can't fill just waits.
- On pop: all 6 players locked out of queueing until their series is reported/resolved.
- **Series timeout**: auto-cancelled (void, no MMR change) after 2 hours with no report (config: `series_timeout_hours`).
- **Mid-series abandonment**: detected by majority vote — **3 of the remaining 5 players** must each report the same player as abandoned (`/abandon`) before the series cancels immediately (void, frees the other 5 right away rather than waiting the full timer).
- **Implemented** (`web/lib/discord/abandon.ts`): `/abandon target:<@user>` infers the series from the channel (`id:` admin-gated override, mirroring `/report`/`/sub`); self-targeting is rejected in application code (not a DB constraint — see migration `0007_subs_abandon.sql`'s comment) since without it a target could vote for themself and short the "3 of the remaining 5" threshold. Votes upsert into `crl6mansqueuebot_abandon_votes` (PK `(series_id, voter_player_id)`, so re-running `/abandon` with a different target overwrites the voter's earlier pick rather than stacking). On the 3rd vote for the same target, settlement uses the same atomic `UPDATE...WHERE status='active'` claim pattern as `/report`, so a simultaneous `/report` and vote-threshold crossing can't double-settle; the losing side just gets "already settled" instead of a corrupted state. A settled void clears any pending `sub_requests`/`abandon_votes` (`clearPendingSeriesState`, `web/lib/discord/matchChannels.ts`) and posts a public "series cancelled" message before the same 30s-delayed channel deletion `/report` uses. **Note**: `/abandon` was fully built but never registered with Discord nor dispatched in `route.ts` — a pre-existing, non-functional-until-fixed gap, closed alongside `/cancel` below.
- **No-fault cancellation**: any of the 6 players can vote to cancel their current match (void, no MMR change) with `/cancel` — unlike `/abandon`, this isn't targeted at a specific player and needs **4 of 6** votes (config-free constant `CANCEL_VOTE_THRESHOLD` in `teamFormation.ts`). Works during both `forming` and `active`. **Revised this session**: the vote message's Cancel button (and the "Cancel" tally field on that embed) was removed — `/cancel` is now the only way to cast a cancel vote, so it isn't offered twice as both a voting-message option and a slash command. `handleCancelButton`/`processCancelButton` (`teamFormation.ts`) and the `cancel:` button dispatch in `route.ts` were deleted as dead code alongside it.
- **Implemented** (`web/lib/discord/teamFormation.ts`): `registerCancelVoteAndMaybeVoid(supabase, series, playerId)` is the shared helper behind both surfaces — casts/re-casts the caller's vote into the same `crl6mansqueuebot_cancel_votes` table the forming-phase button already used (previously undocumented here), so a button click and a `/cancel` run both count toward one shared total regardless of which one is used. At 4 votes, an atomic `UPDATE...WHERE status IN ('forming','active')` claim (same pattern as `/report`/`/abandon`) voids the series, clears pending sub/abandon state, deletes the vote message if one exists, posts a public "series cancelled" message to the queue channel, then follows the same 30s-delayed `deleteMatchChannels` teardown as `/report`/`/abandon` — a no-op during `forming`, since voice channels aren't created until team formation finalizes. `/cancel id:<series_id>` is an admin-gated override for voting from outside the match, mirroring `/report`/`/sub`/`/abandon`'s `id:` pattern; without an override it resolves the caller's series via `getLockedSeriesForPlayer` (checks both `series_lobby` and `series_players`, same as `/abandon`).
- **Per-vote public announcement, added this session** (`processCancelCommand`, `teamFormation.ts`): the caller's confirmation was ephemeral-only, so nobody else in the match saw a cancel vote happening until the 4th vote's public "series cancelled" message — explicit user ask for a simple public embed on every vote below the threshold. Posts `<@caller> wants to cancel {cancelCount}/4` (plain `BRAND_COLOR` embed, no streak-emoji mention decoration, kept deliberately minimal per the request) to `series.queue_channel_id` right after the existing ephemeral reply, skipped once the vote actually crosses the threshold since `registerCancelVoteAndMaybeVoid` already posts its own public "Series cancelled" message in that case. Best-effort (`.catch(() => {})`), matching every other non-critical Discord post in this file.

### Substitutes
- A player who needs to leave mid-series runs `/sub nominee:<@user>` inside their match channel (series is inferred from the channel; `id:` stays available as an optional override for admins running it elsewhere), **nominating a specific replacement**.
- **`/nominate target:<@user> nominee:<@user> [id:]`** (added this session): lets any of the 6 players in a match request a sub **on behalf of another player** in that same match (including themselves, matching `/sub`'s behavior) — for when the player who needs subbing out can't run the command themselves (disconnected, wifi died, etc.). The caller still must be one of the 6 (the series is resolved from *their* own membership, same as every other channel-inferred command), so `/nominate` can't be used by an outsider on a match they're not part of. Accepting and everything past that point works identically to `/sub` — same button, same swap logic, no special-casing.
- The nominee must accept via a button before the swap happens.
- The sub inherits the leaving player's team seat and finishes the series; MMR (Rank Queue only) applies to whoever actually finishes, not the original player.
- Pending sub requests expire after a configurable timeout (`sub_request_timeout_minutes`) so a series can't hang forever on an unanswered nomination.
- **Implemented** (`web/lib/discord/sub.ts`, migration `0007_subs_abandon.sql`): `crl6mansqueuebot_sub_requests` follows the same "existence = pending" convention as `series_lobby`/`queue_members` — a row is deleted (not status-flagged) on accept, expiry, or series settlement, with the leaving player's id as part of the PK so they can't have two outstanding nominations at once. The nominee's own player row isn't created until they click Accept (`getOrCreatePlayer` at that point, using their own interaction payload for the display name) — this sidesteps parsing Discord's `resolved` payload for the USER-type `nominee` option, which the interaction's plain `options[].value` (the nominee's Discord id as a string) is enough for. Acceptance is an atomic delete-claim (`DELETE...WHERE series_id=... AND leaving_player_id=... RETURNING`, same pattern as `admin.ts`'s `removeAdminRole`) so a double-click can't double-accept. On accept: `series_players` swaps the leaving player's row for the nominee's (same team), the nominee is cross-removed from any queue they were sitting in, any `abandon_votes` referencing the leaving player (as voter or target) are deleted as stale, and Discord channel permissions are swapped on both the text channel and the leaving player's team voice channel. **Revised this session** — supersedes an earlier "fixed this session" version of this same bullet that added a `GET /guilds/{id}/voice-states/{user_id}` check before force-disconnecting via `PATCH .../members/{id} {channel_id:null}`: that guard turned out not to reliably prevent the leaving player from getting yanked out of an unrelated voice channel in practice (community-reported: "kicked out of their call no matter what call they are in"), regardless of intent. The manual force-disconnect is removed entirely — deleting the leaving player's member-level overwrite on the team voice channel is sufficient on its own, since Discord enforces voice-channel permission changes on already-connected users in real time: once they lose `CONNECT` on that specific channel (falling back to the `@everyone` overwrite, which denies it — see "Voice channels" below), Discord disconnects them from it within seconds, correctly scoped to that one channel with no risk of touching an unrelated call, since no guild-wide member-move API call is made at all. Before the swap, accept also re-checks `isPlayerLockedInActiveSeries` (exported from `queue.ts`, the same helper `/join` uses) on the nominee — without this, a player already locked into a different active series could accept a sub here and end up in two `series_players` rows at once, double-counting toward MMR; a rejected accept leaves the original player free to `/sub` again with someone else. Pending sub-request expiry is swept every minute alongside the other timeout checks (`web/app/api/discord/sweep/route.ts`), using the same atomic delete-claim so it can't race a last-second Accept click.
- **`/nominate`, implemented this session**: `/sub` and `/nominate` (`handleSubCommand`/`handleNominateCommand`) both funnel into one shared `processSubRequest(interaction, seriesIdOverride, targetDiscordId, nomineeDiscordId, requireExplicitTarget)` — `/sub` calls it with `targetDiscordId: null` (meaning "the caller"), `/nominate` always passes an explicit target. The "leaving player" (self or explicit target) is looked up the same way `/abandon`'s `target:<@user>` already is: among the series' existing `series_players` participants by Discord id, not via `getOrCreatePlayer` — every one of the 6 already has a player row from having queued, so this needs no display-name resolution for the target and mirrors `abandon.ts`'s established pattern rather than inventing a new one. `sub_requests` rows, the duplicate-nomination check, and the Accept button's `custom_id` (`sub_accept:${series.id}:${leavingPlayerId}`) all key off the *resolved target's* player id regardless of who ran the command — which is exactly what makes the entire accept flow (`handleSubAcceptButton`/`processSubAccept`) require zero changes: it was already generic over "whichever player id is encoded in the button," never assumed that player was the one who clicked `/sub`. The only behavioral difference between the two commands is copy: a self-sub still reads "X wants to sub out and nominated you," while a `/nominate`-on-behalf-of-someone-else reads "X nominated you to sub in for Y" so the nominee knows who actually requested it.

### Team formation (on pop)
- **Series-length pre-vote (Best of 3/5/7), added a later session** — feature-flagged via `/admin series-length-vote toggle enabled:<bool>` (config `series_length_vote_enabled`, **default off**, so this doesn't suddenly change behavior for a live community until an admin opts in). When enabled, this vote runs *before* the Balanced/Captains vote below, deciding how long the series is and scaling the K-factor applied at report time: **BO3 = 0.6x, BO5 = 1.0x (no change), BO7 = 1.4x** — a shorter series is higher-variance so it should move MMR less, a longer one is more decisive so it should move MMR more. Mechanically identical to the Balanced/Captains vote: same "first to 3 of 6" resolution, same `vote_timeout_seconds` window. The one behavioral difference: **an unresolved vote at timeout resolves by majority instead of voiding the series** — whichever option currently has the most votes wins, ties (including a 0-0-0 tie if literally nobody voted) favor the *shorter* series (BO3 > BO5 > BO7 preference order). A live 6th-vote tie (only possible as an exact 2-2-2 split, since a 3rd vote for any option would have already resolved it) uses this same tie-break immediately rather than waiting for the timeout.
  - **Implemented** (`web/lib/discord/teamFormation.ts`, migration `0039_series_length_vote.sql`): mirrors the Balanced/Captains vote's shape closely — `crl6mansqueuebot_series_length_votes` (a table shaped like `crl6mansqueuebot_series_votes`, `choice in ('bo3','bo5','bo7')`) stores individual votes; `series.series_length` doubles as both the recorded outcome and the atomic resolution claim flag (`UPDATE ... WHERE series_length IS NULL`), same role `vote_result` plays for the other vote. The K-factor multiplier is written onto `series.series_length_k_multiplier` (numeric, default `1`) at the same moment `series_length` is claimed — a snapshot read unchanged at report time, same precedent as `bonus_day_multiplier`. `resolveSeriesLengthTieBreak(counts)` is a pure, unit-tested function (`teamFormation.test.ts`) shared by both the live-tie and timeout-majority resolution paths.
  - **Message hand-off**: `startSeriesLengthVote` posts the initial vote message and stores its id on `series.formation_message_id` (the *same* column the Balanced/Captains vote already uses) — once the series-length vote resolves, `startTeamFormation` (unchanged otherwise) **PATCH-edits that same message** into the Balanced/Captains vote UI instead of posting a new one, so the whole flow (series-length tally → Balanced/Captains vote → draft-turn UI) reads as one continuously-edited message. `startTeamFormation` gained an optional `existingMessageId` param for this; when absent (feature disabled, or called directly as before), it posts a new message exactly as it always did.
  - **"Chosen!" transition announcements, added a later session** (`resolveSeriesLengthVote`/`castVote`, `teamFormation.ts`) — explicit user request to mark both vote transitions with their own short embed rather than relying purely on the continuously-edited message to communicate what was just decided. Both are a single-line `**bold**` description embed (no title/fields), colored `BRAND_COLOR` (green) normally or `SUPERCHARGED_COLOR` (purple) when `isSuperchargedSeries` — the same green/purple convention every other vote/draft embed in this file already follows, so no new color constant was introduced. **Series-length resolution**: right after `resolveSeriesLengthVote`'s atomic `series_length` claim succeeds, a new, separate `"BO{3|5|7} Chosen!"` message (derived via `winner.toUpperCase()`, not `SERIES_LENGTH_LABELS`'s "Best of N" phrasing) is posted alongside — **additive**, not a replacement for the existing PATCH hand-off directly below it: `startTeamFormation` still PATCH-edits the *same* `messageId` from the series-length tally straight into the Balanced/Captains vote UI, exactly as before. Best-effort (`.catch(() => {})`), since a failed announcement post shouldn't block the real hand-off. **Balanced/Captains resolution**: right after `castVote`'s atomic `vote_result` claim succeeds, the vote message is **deleted** and replaced with a new `"Balanced Chosen!"`/`"Captains Chosen!"` message — this is the one message in the whole formation pipeline that's genuinely swapped rather than PATCH-edited. The new message's id is written back onto `series.formation_message_id` and threaded through to `resolveBalanced`/`beginCaptainsDraft` in place of the now-deleted `messageId`, so downstream reads of `formation_message_id` (`processDraftPick`/`processDraftPickMulti`, which re-fetch it fresh from the DB on every pick) keep PATCH-editing a message that still exists — for Captains mode this means the very next pick prompt (`sendDraftPickPrompt`) PATCHes the "Captains Chosen!" text into the first draft-turn UI moments later, continuing the "one evolving message" pattern from a new starting point rather than leaving it as a separate permanent artifact. For Balanced mode the new id is passed to `finalizeTeams`, whose `messageId` param was already unused (that function only ever posts a fresh "Teams formed!" message and never PATCHes anything) — so "Balanced Chosen!" is left behind as its own short-lived message, same as the vote message it replaced was already left behind unmanaged under the pre-existing (undocumented until now) behavior: `finalizeTeams`'s cleanup only ever touches messages tracked in `crl6mansqueuebot_queue_channel_messages`, a wholly separate system the `formation_message_id`-based vote/draft message has never participated in.
  - **Fair timeout windows**: a new `series.vote_started_at` timestamp tracks "when did the *currently active* vote phase begin," stamped by both `startSeriesLengthVote` and `startTeamFormation` whenever either actually takes over the message. The sweep route's existing Balanced/Captains vote-silence check switched from comparing against `series.created_at` to `vote_started_at` — otherwise, with the pre-vote enabled, the Balanced/Captains vote would inherit whatever time was left on the *original* pop-time clock instead of getting its own full `vote_timeout_seconds` window. A new `series.series_length_vote_active` boolean (set true only while the series-length vote is the current unresolved phase, cleared the moment it resolves) is what lets the sweep route's two timeout checks target disjoint sets of `'forming'` series — without it, `series_length IS NULL` alone can't distinguish "never had a series-length vote" (feature was off) from "has one in progress right now."
  - `web/app/api/discord/sweep/route.ts` gained a new block (checked first, before the existing vote-silence check) that finds series with `series_length_vote_active = true` past the timeout and resolves them via `resolveSeriesLengthByMajority` — this reuses the same claim-and-handoff tail (`resolveSeriesLengthVote`) the live-vote path uses, so both routes converge on identical logic.
  - **Report embed marker**: `reportResultEmbed` (`report.ts`) shows the format next to the existing "🔥 Supercharged" marker (e.g. "Match #123 · Best of 7") whenever `series.series_length` is set, driven by `SERIES_LENGTH_LABELS` (exported from `teamFormation.ts`, reused rather than duplicated). `effectiveKFactor` in both `report.ts` and `adminTools.ts`'s `/admin correct-report` (two independent call sites, per existing precedent for `bonus_day_multiplier`) now multiplies in `series.series_length_k_multiplier` alongside `bonus_day_multiplier` — a no-op (`* 1`) whenever the feature was off for that series. **Superseded a later session**: `series.series_length_k_multiplier` no longer multiplies into `effectiveKFactor` at all — `effectiveKFactor` is now just `kFactor * bonus_day_multiplier` in all three settlement paths (`report.ts`, `adminTools.ts`'s `/admin correct-report`, and `correct.ts`'s `/correct`). Instead it's passed to `computeEloDeltas` as the new `EloConfig.seriesLengthMultiplier` field (`elo.ts`), applied as the very last step of the per-player delta computation — after skew dampening and after `minDeltaFloor` is added, multiplying the whole fully-formed delta rather than folding into `kFactor` before the delta math runs. Root cause: folding it into `kFactor` only scaled the K-scaled "earned" `score-expected` term, which `minDeltaFloor`'s flat, non-scaling add-on could dwarf on a near-certain result — a heavy BO7 favorite winning as expected landed barely ahead of the same BO3 win, since the scaled term was tiny and the flat floor dominated both, contrary to the intent of BO7 mattering more than BO3. Applying the multiplier last instead scales the floor too, so BO3/BO5/BO7 stay proportionally 0.6x/1.0x/1.4x apart regardless of how lopsided the win was. Direct user request, diagnosed live against a real match card's numbers. Covered by two new unit tests in `elo.test.ts` (`describe("computeEloDeltas — series length multiplier", ...)`).
  - **Embed copy simplified, added a later session** (`voteEmbed`/`seriesLengthVoteEmbed`, `teamFormation.ts`): both vote-tally embeds' descriptions were trimmed to a single sentence with only the minute count bolded — the series-length vote reads `"You have **N minutes** to vote on series length!"`, the Balanced/Captains vote reads `"You have **N minutes** to vote!"` (`minutes = Math.round(timeoutSeconds / vote_timeout_seconds / 60)`, singular/plural handled). The series-length vote's three `Best of N` fields also gained a per-option "worth" header — each field's `name` is now the option's `SERIES_LENGTH_K_MULTIPLIERS` value as a percentage (`"60%"`/`"100%"`/`"140%"`, rendered above `"Best of 3\nX / 3"` etc. in the `value`) — so the K-factor tradeoff is visible on the vote itself rather than only discoverable via `/report`'s post-hoc marker or this file.
- Players vote **Balanced** vs **Captains**; first option to reach 3 votes (of 6) wins.
- Players may set a personal **default vote preference** (`/vote-default`), auto-cast each pop, still overridable per-game.
- Exact 3-3 tie resolves to **Captains**.
- **Captains mode** (default): captains are drawn from **ranked (placed) players first** — revised this session, supersedes the earlier "top three of the whole lobby by MMR" version below, which didn't distinguish ranked from unranked players at all. Four scenarios, by how many of the 6 lobby members are currently ranked (`is_placed`):
  - **3+ ranked**: two of the top three *ranked* players by MMR are chosen at random to be captains (unchanged mechanic from before — randomly exclude one of the top three, the other two captain — just now scoped to the ranked subset rather than the whole lobby). The excluded top-three player returns to the regular draft pool alongside the rest, ranked or not.
  - **Exactly 2 ranked**: both become captains outright, no randomness.
  - **Exactly 1 ranked**: that player is one captain; the other is a random pick from the top two *unranked* players by MMR.
  - **0 ranked**: same shape as the 3+ case, but sourced entirely from the unranked pool — two of the top three unranked players by MMR, chosen at random.
  Unranked players are only ever drawn on to fill a captain slot ranked players couldn't fill, never to displace one — a 4th/5th/6th ranked player is still ignored in favor of an unranked player only when there are fewer than 2 ranked players total to begin with. "Worst two in lobby" exists as a config toggle, not default — scope is always within the 6-player lobby, never full-server MMR. Draft order for the remaining 4 players (decided an earlier session): **Captain 1 picks one player, then Captain 2 picks two players, then the last remaining player auto-assigns to Captain 1's team** (no button click needed for that final auto-assign — only 4 total picks/choices happen, not an alternating snake).
  - **Implemented** (`web/lib/discord/teamFormation.ts`'s `selectCaptainCandidates`, unit-tested in `teamFormation.test.ts`): a pure function taking the 6 lobby members and returning the 2 (unordered) captain candidates per the rules above. **Revised this session**: which of the two chosen candidates becomes Captain A (picks first) is now a coin flip (`beginCaptainsDraft`) rather than "whichever has higher MMR" — supersedes that earlier convention, since preferring ranked players for the captain slots themselves shouldn't also mean the higher-raw-MMR one always picks first (this matters most in the 1-ranked scenario, where the random unranked co-captain could otherwise out-MMR the sole ranked captain and always go first). Superseded a prior version that always ran "two of the top three of the whole lobby by MMR, chosen at random" with no ranked/unranked distinction at all.
- **Balanced mode**: brute-force all 10 unique 3v3 splits of the 6 players (C(6,3)/2), pick the split with the smallest team-strength difference between teams (see "MMR / Elo" below for the team-strength formula — revised this session, no longer a plain average). No snake draft — brute force is strictly better at this scale.
- **Implemented** (`web/lib/discord/teamFormation.ts`): captains-draft state lives directly on `series_lobby` rows (`is_captain`, `team`) rather than a separate draft-state table — whose turn it is is derived by counting how many non-captain rows already have a `team` set, not stored. Draft picks and vote casts both use an atomic `UPDATE ... WHERE column IS NULL` claim (relying on Postgres row locking) instead of an advisory lock, since each is a single-row race. One Discord message (`series.formation_message_id`) is PATCH-edited through vote tally → draft turn UI → final teams-formed summary, mirroring the persistent-queue-message pattern from Phase 2 — **revised a later session**, supersedes the original "created once and PATCH-edited" framing: `formation_message_id` is now swapped to a brand-new message id once, right when the Balanced/Captains vote resolves (see the "Chosen!" transition announcements bullet above) — the vote message itself is deleted rather than PATCH-edited at that one transition, with everything before and after it (vote tally → "Chosen!", "Chosen!" → draft turn UI → teams-formed) still a continuously-edited/freshly-posted chain exactly as before.
- **Private match credentials, added this session** (`web/lib/discord/teamFormation.ts`'s `finalizeTeams`, migration `0024_private_match_credentials.sql`): once teams are finalized — the same single function both the balanced-split and both captains-draft completion paths funnel through, so this needs no per-path duplication — the bot generates a 4-random-digit password (`Math.floor(Math.random() * 10)` per digit, joined; leading zeros allowed, e.g. `"0483"`) and best-effort DMs each of the 6 real players (test-data bots skipped, same guard the draft-pick confirmation DM uses) an embed with two fields: **Name** (always the literal constant `crlw6m`) and **Password** (that series' generated digits). The password is stored on `series.private_match_password` — write-once, never displayed anywhere else (report summary, leaderboard) — purely so it exists somewhere server-side if a support question ever needs it. Not regenerated on `/sub`/`/nominate` — a mid-series substitute joins the same already-created private match, so they'd need the same credentials as everyone else, not new ones; the DM would need to be re-sent to the substitute specifically for this to fully work, an accepted gap for now since it wasn't part of the request.

### MMR / Elo
- Standard Elo, single rating per player, starts at **0** (can go negative — no floor/ceiling).
- **Team rating/strength formula, revised this session** — supersedes the original plain 3-player MMR average. `calculateTeamStrength()` (`web/lib/mmr/teamStrength.ts`) instead weights the top two of a team's 3 ratings via a generalized power mean, blended with a small contribution from the weakest player, so a strong duo carrying a weak third player rates higher than a flat average would:
  ```
  sort ratings descending -> strongest, second, weakest
  topTwoCore = ((strongest^0.785699 + second^0.785699) / 2) ^ (1 / 0.785699)
  teamStrength = (1 - 0.036555) * topTwoCore + 0.036555 * weakest
  ```
  Both exponent (`0.785699`) and weakest-player weight (`0.036555`) are fixed constants, not admin-configurable — supplied as-is by the user, not derived. Since MMR has no floor and can go negative but this formula's fractional exponentiation is undefined for negative bases, each rating is first transformed onto a positive scale — `mmr * scale + shift` (fixed constants specific to this formula, distinct from the leaderboard's admin-configurable display-only `mmr_scale`/`mmr_shift`, which never feed into internal comparisons — same precedent as `hysteresis_mmr`) — then clamped at 0 as a backstop for anything still negative after the shift. This is a pure function of the 3 ratings with no knowledge of *which* 3 they are, so one implementation serves all consumers below with no duplicated logic: the Elo engine's team rating (this section), the balanced-split brute force's team comparison (see "Team formation (on pop)" above), `/chances`, and the History page's win-odds bar all call it identically, preserving the invariant that team strength has one consistent definition used everywhere it's needed.
  - **No round-trip, revised this session** — supersedes the original design, which shifted/scaled by `mmr * 5 + 1600` and then **inverted the result back down to raw-MMR units** before returning (`(strength - 1600) / 5`), specifically so a uniform (no in-team spread) team round-tripped back to exactly its plain average and `S`/`K` stayed calibrated to raw-MMR-sized gaps with no retuning needed. The user explicitly rejected this round-trip: walking through a worked example (two 3-player rosters), they clarified the shift/scale is meant as a **one-way** move into a different predictor's numeric range — "don't undo the shift/scale" — not a transform to be undone before comparison. `calculateTeamStrength()` now transforms with `scale = 3.5`, `shift = 1550` (both changed from `5`/`1600`) and returns the blended value **directly in that shifted/scaled space**, with no inverse step. Since `E_A = 1/(1+10^((R_B-R_A)/S))` (below) now compares two much-larger-magnitude numbers than raw MMR without `S` being retuned to compensate — **`S` stays at its existing default of 400, admin-configurable, deliberately not retuned**, per the user's explicit choice after being shown the consequence — the same worked example's win-probability split went from 41.4%/58.6% (old, round-tripped formula) to 22.7%/77.3% (new formula): ordinary MMR gaps now swing the expected score, and therefore the K-factor split and every reported match's real Elo delta (not just display-only predictions like `/chances`), much closer to the extremes than before this change.
- `E_A = 1 / (1 + 10^((R_B - R_A) / S))`, `R_new = R_old + K * (Score - E)`. Score = 1 win / 0 loss. Point change splits evenly across the 3 teammates. `R_A`/`R_B` are each team's `calculateTeamStrength()` value, not a plain average.
- Defaults: `S = 400`, `K = 32` (both admin-configurable).
- **Provisional K**: elevated K-factor (config multiplier, default 1.75x) for a player's first N **Rank Queue** games (config `provisional_games`, default 10), then drops to standard K.
- **Win-streak bonus** (added this session — supersedes the prior "no flat streak bonus anywhere" stance): Rank Queue only, no effect on Universal Queue. A player's per-game bonus is a function of their *prior* consecutive-win streak (before the game being scored): 0 below a 3-game streak, then +1 MMR per game starting at a 3-game prior streak (3→+1, 4→+2, 5→+3, 6→+4, 7+→+5 cap). A single loss resets the streak to 0 (and thus the bonus) immediately. At a **5+ game streak**, every reported match that extends it also posts an extra amber-colored embed: "`<mention> is on a # game win streak!`". Independently of the bonus and the announcement embed, any player currently on a **3+ game streak** (lowered from 5+ this session — a deliberately different, lower threshold than the announcement embed above) gets a 🔥 appended after their `@mention` in every bot-authored message that mentions them (queue status, vote/draft, teams-formed, sub/abandon embeds) — this is bot-message-only decoration (no nickname mutation, no extra Discord permission), not tied to the MMR-bonus toggle below.
  - **Implemented** (`web/lib/mmr/elo.ts`'s `computeStreakBonus`, `web/lib/discord/streaks.ts`, wired into `web/lib/discord/report.ts` and `web/lib/discord/adminTools.ts`'s `/admin correct-report`): streak length is **computed live from report history**, not stored as a counter column — mirrors the leaderboard's existing win-streak columns (`web/lib/leaderboard/queries.ts`'s `getAllPlayersWithGames`). `streaks.ts` exposes `getPriorRankWinStreak` (single player, with an `excludeSeriesId` param — required at report/correction time since the atomic settle claim flips the series to `status='reported'` *before* the Elo/streak block runs, so the in-flight series must be excluded or it double-counts as its own most recent result) and the batched `getStreakIds` (no exclusion — used everywhere else, since those call sites render after any relevant series has already settled; renamed from `getOnFirePlayerIds` this session when it grew a second, cold-streak set — see below). Two separate constants in `streaks.ts` back the two different thresholds: `ON_FIRE_THRESHOLD = 5` (the announcement embed, checked directly in `report.ts`) and `FLAME_THRESHOLD = 3` (the 🔥 mention decoration, used by `getStreakIds` and report.ts's own summary-line `onFire` check) — kept as two constants rather than one so the flame threshold can move independently of the announcement embed's, which is exactly what happened this session. The bonus is folded directly into the existing `series_players.mmr_delta` value rather than tracked separately, so `/admin unreport`'s existing `mmr -= mmr_delta` unwind reverses it with no new code. `/admin correct-report` recomputes the bonus for the new winning team but doesn't re-fire the announcement embed or account for later games played since — an accepted limitation of correcting a match after the fact.
  - **`/admin streak-bonus toggle enabled:<bool>`** (config `streak_bonus_enabled`, default on — same precedent as `bonus_day_enabled`/`queue_simplified_messages`: listed in `KNOWN_CONFIG_DEFAULTS` for `/admin config get`'s display but kept out of the generic `/admin config set`'s key list, its own dedicated boolean-validated subcommand instead) disables **only** the MMR-bonus arithmetic — streak tracking, the amber announcement embed, and the fire-emoji mention decoration all keep working regardless, per explicit spec.
  - **Cold-streak (losing-streak) decoration** (added this session): mirrors the 🔥 mention decoration for the opposite case — any player currently on a **3+ game losing streak** (`COLD_THRESHOLD = 3`, `web/lib/leaderboard/stats.ts`, same value as `FLAME_THRESHOLD`) gets a 🥶 appended after their `@mention` in the same set of bot-authored messages the fire decoration already covers (queue status, vote/draft, teams-formed, sub/abandon embeds), plus the Main leaderboard next to their name (`web/components/LeaderboardTable.tsx`). **Purely cosmetic** — no MMR effect, and deliberately no announcement-embed equivalent to `ON_FIRE_THRESHOLD` (out of scope per the request). Rank Queue only, test-data excluded — same filters as the win-streak system. **Implemented**: `streaks.ts` gained `getPriorRankLossStreak` (mirrors `getPriorRankWinStreak`, same `excludeSeriesId` handling) and `getStreakIds` now returns `{ onFireIds, coldIds }` from one shared batched query pass (`fetchStreakGames`/`gamesByPlayer`) instead of two separate queries. `mention()`'s signature changed from a single `onFire: boolean` param to a `{ onFire?: boolean; cold?: boolean }` object so both decorations can be expressed through one call — a player is never both at once (opposite streak types) but the flags are independent booleans rather than an enum. `report.ts`'s settle logic computes a losing-team player's own consecutive-loss count for the first time (previously losers were hardcoded to a `0` streak, since only the win-streak bonus existed) via a `newLossStreakById` map built in parallel with the existing `newStreakById`/`priorStreakById` win-streak maps. `web/lib/leaderboard/stats.ts`'s `GameStats.currentStreak` already supported `{ type: "L", count }` for losing streaks, so no interface change was needed there — just the new `COLD_THRESHOLD` constant and `UnifiedLeaderboard.tsx` checking `currentStreak.type === "L"` against it alongside the existing `"W"`/`FLAME_THRESHOLD` check.
- **Implemented** (`web/lib/mmr/elo.ts`, wired into `web/lib/discord/report.ts`): a `players.rank_games_played` counter (migration `0006_reporting_mmr.sql`) tracks the provisional-K window specifically — distinct from `total_games_played`, which counts both queues for placement bootstrap. When teammates have different provisional status on the same result, each player applies their *own* K to their third of the (Score − E) split rather than blending the three into one team K — the spec's "elevated K for a player's first N Rank Queue games" is a per-player property, so this isn't zero-sum across teams when K differs, which is expected. Each reported series' exact per-player delta is stored on `series_players.mmr_delta` (also added in `0006`) so a future `/admin unreport` (Phase 8) can unwind it exactly, without needing to reconstruct a reverse delta after later games have already moved everyone's rating.
- **Skew factor + minimum delta floor** (added this session, `web/lib/mmr/elo.ts`, both optional on `EloConfig` and no-ops when 0/omitted, so `elo.test.ts`'s original baseline tests are unaffected): validated first via standalone simulations in `web/scripts/simulate-mmr-skew.mjs` and `simulate-mmr-participation.mjs` before being ported into production code.
  - `mmr_skew_factor` (config, default `0.5`): dampens a player's per-game delta with a Gaussian falloff (`exp(-mmr²/(2·σ²))`, `σ = 50·(1-min(|skewFactor|,0.9))`), but only in the direction that would push them further into whichever side the sign of `skewFactor` designates as dampened (positive `skewFactor` → negative side dampened). Deltas moving a dampened-side player back toward 0 are never touched. This makes the mechanic asymmetric by design — for a player sitting below 0, a loss (pushed further negative) shrinks while a win (pulled toward 0) doesn't, so it can't trap a player at a low rank the way a symmetric dampening would; a negative `skewFactor` mirrors the same asymmetric protection onto the positive side instead. **Revised this session**: the Gaussian is centered on the *midpoint* between the player's current MMR and their raw, pre-dampening outcome MMR (`midpointMmr = mmr + rawDelta/2`, exactly the average of `mmr` and `mmr + rawDelta`) rather than on current MMR alone — this also decides which side of 0 the player is considered on for the dampening check, not just the multiplier's input. Superseded the earlier "tied to their *current* MMR" version: a player sitting just above the dampened-side boundary who's about to be pushed across it by this exact game's raw delta previously got zero protection, since their pre-game sign didn't match the dampened side yet even though the outcome would; averaging in the outcome catches that case instead of only reacting a game late, at the cost of also dampening more aggressively for players already deep on the dampened side (the midpoint sits further from 0 than current MMR alone, shrinking the multiplier further).
  - `mmr_min_delta` (config, default `2`): applied last, adds a fixed floor to *every* nonzero delta's magnitude in the direction it was already headed (e.g. `-0.02 → -2.02`, `+5.32 → +7.32`) — not a clamp on only-small deltas, it inflates large ones too. Widens overall MMR spread and introduces a small positive correlation between games played and final MMR (not present in plain Elo, which is a martingale) since the fixed floor isn't exactly zero-sum per game once win/loss expectation isn't exactly 0.5.
  - Both apply to every `computeEloDeltas` call site: `/report` (`report.ts`) and `/admin correct-report` (`adminTools.ts`); `/admin unreport` is unaffected since it reverses the already-stored `series_players.mmr_delta` directly rather than recomputing.

### Weekly bonus day
- A recurring **range of days** (default **Saturday only**) during which Rank Queue's K-factor is multiplied by a configurable bonus (default **+50%**, i.e. K x1.5). Universal Queue is unaffected — it never runs Elo.
- **Revised this session — supersedes the original single-day design**: a `bonus_day_of_week` config value is now a `bonus_day_start`/`bonus_day_end` pair, each independently admin-settable, so the bonus can span more than one day (e.g. a whole weekend, or the whole week) instead of exactly one. Range membership is inclusive and **wraparound-aware**: a range like Friday(5)→Sunday(0) means Fri/Sat/Sun rather than matching nothing, so every start/end combination is meaningful and no start-must-be-before-end validation is needed. `start === end` is a single bonus day — the original behavior, and still the default (Saturday/Saturday).
- Window starts at midnight **Pacific time** on the range's start day and ends at midnight **Pacific time** the day *after* the range's end day (the `America/Los_Angeles` zone, so it tracks the PDT/PST switch rather than a fixed UTC offset). E.g. start=end=Sunday means only Sunday (12am Sunday to 12am Monday) is boosted; start=Sunday, end=Saturday means the entire week is boosted.
- **Eligibility is decided by when the queue completes (pops to 6/6), not when the match is reported** — a series that pops inside the window keeps the bonus even if it's reported after the window has since closed; team formation doesn't need to have finished, just the pop.
- On by default (`bonus_day_enabled`); bonus percentage (`bonus_day_bonus_pct`, default 50), range start (`bonus_day_start`, default 6/Saturday), and range end (`bonus_day_end`, default 6/Saturday) are all admin-tunable, Sun=0..Sat=6.
- **Implemented** (`web/lib/discord/bonusDay.ts`, migrations `0022_bonus_day.sql`/`0037_bonus_day_range.sql`): `computeBonusDayMultiplier()` is evaluated once, at series-pop time (`handlePop`, `queue.ts`), and the resulting multiplier (1 = no bonus) is written straight onto the series row (`bonus_day_multiplier`) instead of being recomputed at report time — this is what makes the "queue completes before the window ends" rule work, since by the time `/report` runs the window may already be closed. `/report` (`report.ts`) and `/admin correct-report` (`adminTools.ts`) both multiply the fetched `k_factor` by the series' stored `bonus_day_multiplier` before calling `computeEloDeltas` — no change to `elo.ts` itself, since the bonus is a flat per-series K adjustment rather than a per-player one, so it composes cleanly with the skew/min-delta-floor mechanics above (those act on whatever delta falls out of the already-bonus-adjusted K). The report summary embed shows a "🔥 Bonus Day" marker when it applied. The range check itself is a pure, unit-tested `isDayInRange(day, start, end)` helper in `bonusDay.ts` (`bonusDay.test.ts`), consumed only by `computeBonusDayMultiplier()` — `currentPacificDayOfWeek()` (also in `bonusDay.ts`) is unchanged and still independently reused by `matchTimeStats.ts`'s unrelated day-of-week analytics histogram. Four dedicated `/admin bonus-day` subcommands (`toggle`, `set-bonus`, `set-start-day`, `set-end-day`) manage the four config keys, kept out of the generic `/admin config set`'s key list — same precedent as `bot_paused`/`stop`/`start` — so the day commands get Discord-native day-of-week choices and `set-bonus` gets its own bounds check; `set-start-day`/`set-end-day` share one handler (`processBonusDaySetRangeEnd`, `adminTools.ts`) parameterized by which config key to write, and each confirms the resulting *combined* range (not just the one endpoint that changed) by reading the other endpoint back before replying. Migration `0037_bonus_day_range.sql` retires `bonus_day_of_week`, migrating any previously-configured value into both new keys as a single-day range first (same retirement pattern as `hysteresis_pct` → `hysteresis_mmr`, `0028_hysteresis_mmr.sql`) — **needs manual production application**, same as every other recent migration (this sandbox has no DB write access). The Info page's "Bonuses" section (`web/app/info/page.tsx`) renders the singular "Bonus Day is Saturday" phrasing when `start === end`, and a "Bonus Range runs from X through Y" phrasing otherwise.

### Bands / ranks
- 4 percentile-based bands (Mohs-hardness themed): **Iron → Garnet → Emerald → Sapphire**. **Prism** (revised this session — supersedes the original season-end-only design below) is a **live**, ungated Top-N tier (config `prism_top_n`, default **1** — lowered from an earlier default of 5 in a later session, see below) layered on top of the 4 real bands: whoever is currently Sapphire band and in the top N of Sapphire players by MMR (among players meeting `top10_min_games` for the *current* season — see the "Sapphire prerequisite" bullet below) holds it, and falls back to Sapphire the instant they drop out of any of those three conditions — no grace period, no hysteresis, unlike ordinary demotion. Still not part of `BAND_ORDER`/the daily percentile-loop's 4 values — kept as a separate overlay pass specifically so it never gets routed through `computeBandChange`'s grace/hysteresis machinery, which has no promotion threshold above Sapphire and so could never demote a within-`BAND_ORDER` Prism tier.
- **Prism restricted to the single top-ranked player (revised a later session)**: `prism_top_n`'s default dropped from 5 to 1 — deliberate design change, not a bug fix. At `prism_top_n=5` in a small community, a majority of active/eligible players could hold Prism simultaneously, undermining its exclusivity. This was initially misdiagnosed as a bug report ("bottom band players can't be Prism") before the user clarified it was the intended behavior they wanted, just needing the threshold tightened from top-5 to top-1. If `prism_top_n` was ever explicitly set via `/admin config set` on the live Discord server, the DB-stored value overrides this code default (`getConfigNumber`'s precedence rule) and needs updating there too for the change to take effect in production.
- **Games-played eligibility does not have priority over MMR rank, fixed a later session** (`recomputeBands()`, `web/lib/discord/bands.ts`): the original implementation filtered candidates by `top10_min_games` *before* sorting by MMR and slicing to `prism_top_n` — so a lower-MMR player who happened to have played enough Rank Queue games this season could occupy a Prism slot that a higher-MMR player, who simply hadn't hit the games-played threshold yet, would otherwise hold. Caught via a live production example: with `prism_top_n=5` set on the Discord server, 4 separate players (ranked #1, #5, #6, #8 by MMR) all held Prism at once, because only 3 of the top 5 by MMR had played enough games this season and the games-eligible #6/#8 backfilled the empty slots. **Fixed**: MMR rank now determines the top-`prism_top_n` candidate bracket first (ties broken by season games played, then player id — same tiebreak the daily band recompute already uses), and `top10_min_games` is applied only as a filter *within* that already-fixed bracket — it can never pull in a replacement from outside it. A top-N slot with no games-eligible occupant simply goes unfilled that cycle rather than falling through to whoever's next by MMR. **Invariant to remember**: Prism holders are always a subset of the top-`prism_top_n`-by-MMR bracket (0 to `prism_top_n` players, never more) — never a player outside that bracket, regardless of how many games they've played. At the default `prism_top_n=1` this reduces to "only the single highest-MMR eligible player, or nobody if they haven't hit `top10_min_games` yet." `web/lib/discord/seasonClose.ts`'s separate archival `made_top10` computation (season-close standings) was not touched by this fix — it wasn't reported as broken and hasn't been discussed with the user.
- **Sapphire prerequisite, added a later session** (`recomputeBands()`, `web/lib/discord/bands.ts`): Prism eligibility is now three ANDed requirements applied as a strict funnel, each narrowing the pool the next stage ranks/filters over with no backfilling from a player excluded at an earlier stage — (1) **already Sapphire band** (the real band assignment, computed earlier in the same `recomputeBands()` pass, so `player.band` already reflects this cycle's value) — this is new: previously a small community's Emerald/Garnet players could occupy top-`prism_top_n`-by-MMR slots purely because the pool was thin, even though they weren't in the top real band at all; (2) top `prism_top_n` by MMR **among Sapphire players only**, not the top N of the whole placed pool — so a 6th- or 7th-place-overall Sapphire player can still take a slot rather than losing it to a higher-raw-MMR non-Sapphire player; (3) `top10_min_games` this season, checked last as before — unfilled if not met, never backfilled from the next-ranked Sapphire player (unchanged from the fix above). Explicitly requested by the user as "prism rank [Sapphire], play at least N games, and be top N" after confirming via a clarifying question that "prism rank" meant the Sapphire band specifically.
- **Prism made a season-end achievement, then reverted back to a live rank (2026-08-29/30 session) — supersedes the achievement design, and revises the funnel ordering in the two bullets above.** An intervening session had converted Prism from the live overlay described above into a season-close-only achievement: computed once in `seasonClose.ts`, held *additively* alongside the player's real band instead of displacing it, surviving the soft reset, and rendered as a brightened tint of the player's own band color rather than a Prism icon/label; the leaderboard meanwhile grew a *separate* always-fills-`prism_top_n` "would be Prism" gold-row preview. That change was never written up here. The user reverted it after community feedback — verbatim: *"prism is going back to being like it was before where its a standard rank"* — so everything above is live and current again: Prism is recomputed on every `recomputeBands()` call, substitutes for the player's band at every icon/label/color site (`is_prism ? "Prism" : band`), is cleared by the season soft reset, and swaps the Sapphire Discord role for the Prism role via the ordinary `reconcileMemberRole` path. **One rule did *not* come back unchanged — the funnel is now qualify-then-cut, not cut-then-filter.** The user restated the requirements as *"must be sapphire elegible, has the min topN\_min\_games, there is N prism holders ... must be placed, MMR desc"*: placed AND Sapphire AND `>= top10_min_games` are now all **qualification filters applied before** `.slice(prism_top_n)`, sorted MMR desc (ties: season games, then player id). So the N slots fill from the qualified pool whenever enough players qualify, and a qualified lower-MMR player is never held out by an unqualified higher-MMR one. This deliberately drops the "a top-N-by-MMR slot with no games-eligible occupant simply goes unfilled" invariant from the games-played bullet above — the community was seeing 2 Prism holders with `prism_top_n=5`, which is what prompted the restatement. Fewer than N holders now happens only when fewer than N players qualify at all. The leaderboard's separate gold "would be Prism" preview was collapsed back onto live Prism: gold rows == current Prism holders, one flag (`isPrism`) driving icon, label, color and gold row/stat text, so gold and the Prism icon can never disagree. **The avatar glow is the one Prism affordance deliberately *not* on that flag** (corrected 2026-08-30, same session, after the user caught the regression: *"have these changes removed the glowing effect around players if they finished prism the previous season because I wanted to keep that feature"*). The glow was born in the achievement era (`b4fc8a0`; `PlayerAvatar` had no `glow` prop before it) and has only ever meant **"finished the last closed season inside that season's Prism cut"** — the revert silently repurposed it into "holds Prism right now," which would have erased every alumnus at the next `/newseason` since the soft reset clears `is_prism`. It's now a separate `wasPrism` row flag on both leaderboard views, sourced from the archived `season_history.made_top10` of the most recently closed season (`prismAlumniIds` in `UnifiedLeaderboard.tsx`) — no migration, the column already existed. A past-season board glows for **that** season's own `made_top10` instead. Current Prism holders therefore do *not* glow unless they also finished last season in the cut; gold row and glow are allowed to disagree, and until season 1 closes the alumni set is empty so nothing glows on the live board at all. Hall of Fame's glow is unrelated and unconditional (`HallOfFameSlotCard.tsx`). Archived seasons on the leaderboard still read their Prism marker from the stored `made_top10` flag rather than today's live `is_prism` or a re-cut with today's config. `prism_top_n` is **5** on the live server (not the code default), so expect up to 5 holders the first time bands recompute after deploy.

- **`made_top10` is now a snapshot of `is_prism` at close, not a second top-N computation (2026-08-30, same session)** (`web/lib/discord/seasonClose.ts`). Supersedes the `made_top10` descriptions in the games-played-eligibility bullet above and in "Top N / Prism role" / the `closeSeason()` implementation bullet below. The revert left two different rules in the codebase: `bands.ts` selects live Prism as placed AND Sapphire AND `>= top10_min_games`, then the top `prism_top_n` by MMR (qualify-then-cut), while `closeSeason()` still archived the top `prism_top_n` by MMR among players with `>= top10_min_games` and **no** band/placed qualification — so whenever fewer than N players qualified for live Prism, the archive backfilled those slots from lower bands and would have recorded (and, next season, glowed) players who never held the rank. The user settled it: *"the players who receive the glowing effect are the ones who ended the season as being prism."* `closeSeason()` now writes `made_top10: r.player.is_prism`, read off the player rows it already fetches pre-reset — no re-derivation, no shared helper, no possible drift, and the `top10_min_games`/`prism_top_n` config reads were dropped from that function entirely (`bands.ts` owns both). Ordering already guaranteed this works: the history upsert runs before `applyMmrDecay`/`resetAllPlacementsToUnranked`, and the reset is what clears `is_prism`, so the flag is still live at archive time. `recomputeBands()` refreshes `is_prism` on every Rank Queue report and on the daily cron, so the snapshot is the standing the community actually saw at close.
- **Bands gate nothing — Rank Queue is open to everyone immediately, no placement requirement** (revised this session; supersedes the original placement-gated design below). There is a single shared `#rank-queue` channel, not one channel per band — the bot pools all Rank Queue joins together with no band segregation in matchmaking (same simple join-order pop as Universal Queue). The `Unranked` role (named `Placed` in an earlier draft of this doc — code and DB always used `Unranked`, doc corrected this session) still exists and is still granted/revoked on band change, but it's now purely informational (confirms a player has queued/placed) rather than an access gate (decided this session, see "Discord bot commands & channels" below).
- **`Unranked` role is granted the instant a player first ever runs `/q`/`/queue`** (added this session, `grantUnrankedRoleToNewPlayer` in `bands.ts`, hooked into `getOrCreatePlayer`'s new `onCreated` callback in `queue.ts` — fires only on the player row's initial insert, not on every subsequent join) — they don't need to pop a match, just queue once. The daily recompute then **removes** `Unranked` and grants the player's real computed band the moment they actually cross `placement_games_required` (same code path as any other promotion/demotion — see `Implemented, Phase 5` below), so `Unranked` behaves as a genuine transitional "queued but not yet banded" state rather than a permanent post-placement badge.
- Cutoffs (percentile ranking over all **placed** players' MMR) are recomputed **daily** — this stays the source of truth for anyone who hasn't just played. **Revised this session**: on top of that, every reported Rank Queue series now also triggers a live recompute scoped to just its 6 players (percentile still computed against the whole pool, only the write/role-sync/DM is scoped) — see "Reporting & disputes" below. A player's band can now change the instant their match is reported, not just at the next daily tick.
- **Band calc mode — two ways to turn the placed pool's MMR ordering into a percentile, added this session** (`/admin band-calc-mode mode:<position|mmr>`, config `band_calc_mode`, `computeBandPercentiles()` in `web/lib/discord/bands.ts`): raised by the user pasting a live 9-player leaderboard where band assignment clearly wasn't tracking actual MMR gaps between players. **`position`** (default, original behavior): purely rank-order — `(index / n) * 100`, 0-indexed — so the lowest-MMR player in the pool sits at 0th percentile and the highest at `(n-1)/n*100`, evenly spaced regardless of how close or far apart players' real MMR values are; a pack of players a single point apart spreads across percentiles exactly as if they were hundreds of points apart, as long as nobody else sits between them. **`mmr`**: percentile instead reflects where a player's raw MMR falls within the pool's actual MMR range — `(mmr - min) / (max - min) * 100` — so a tight cluster of similar MMRs stays clustered in percentile too, and a standout player's real lead shows up directly instead of being flattened to "one rank above the next player"; falls back to `50` for every player when the whole pool is tied on MMR (zero range), rather than dividing by zero. Both modes share the same tiebreak order for the underlying sort (MMR, then `total_games_played`, then player id). This only changes how `percentileById` is built inside `recomputeBands()` — `targetBandForPercentile`/`computeBandChange`'s grace/hysteresis logic downstream is unchanged and mode-agnostic, since it only ever sees the already-computed percentile number. Takes effect on the next recompute (daily cron, next Rank Queue report, or an immediate `/admin recompute-bands`) — not retroactive. Not consulted by the live Prism overlay, which has always ranked by raw MMR directly rather than by percentile. **Switching modes should be followed by `/admin recompute-bands force:true` once**: a plain recompute right after a switch still routes every demotion through grace/hysteresis per player, so the new percentiles only apply gradually and unevenly (some players blocked by grace, others held inside the hysteresis buffer) rather than all at once — `force:true` bypasses both for that one run, same remedy this file already documents elsewhere for players stuck at an inflated band. The command's own reply text says this every time so an admin doesn't have to remember it, and re-setting the same mode it's already on is a no-op (doesn't touch config, log, or repeat the reminder).
- **Placement**: a player is unbanded (`is_placed = false`, shows `NA` band/MMR on the leaderboard) until `rank_games_played >= placement_games_required` (config, default 10; **Rank Queue games only**, revised this session — see "Placement bootstrap" below). Prevents a day-1 Sapphire off a lucky streak from zero games. No longer gates Rank Queue access (see above) — only controls whether they're included in the daily percentile pool and shown a real band.
- **Promotion**: immediate (at whichever recompute — daily or per-report — next evaluates the player) if MMR percentile crosses into a higher band. No safeguard needed.
- **Demotion**: two stacked safeguards, grace checked first —
  - **Grace period**: first **3** Rank Queue games played in a new band are demotion-immune regardless of standing (config `grace_games`; the original spec doc said 2 — superseded by the Q&A doc's answer of 3). **Grace-inactivity bypass** (added this session): `band_games_played` only advances when the player actually reports a Rank Queue game, so a player who promotes and then stops playing entirely would otherwise stay demotion-immune forever, even as the pool shifts under them. If a player has gone `grace_inactivity_days` (config, default **7** — one week) since their last Rank Queue game, grace is treated as expired regardless of `band_games_played` — this only unlocks the hysteresis check below, it never demotes by itself, and it never fires for a player who's still actively playing (every reported game refreshes their last-played timestamp, so grace still only expires by games played for someone who keeps queuing — this part is unchanged).
  - **Hysteresis buffer**: after grace expires (by either games or inactivity), only demote if the player's raw MMR has fallen more than a fixed `hysteresis_mmr` (default **7**) MMR points below their current band's threshold MMR — **revised this session, supersedes the original percentile-based `hysteresis_pct` buffer**. The threshold MMR for each band (Garnet/Emerald/Sapphire) is derived from the same percentile cutoffs as before, just converted into a concrete MMR value via `computeBandThresholdMmr()` (`web/lib/discord/bands.ts`) rather than compared as a raw percentile: `mmr` mode linearly interpolates within the placed pool's MMR range (`min + cutoffPercent/100 * (max - min)`), `position` mode takes the MMR of the player sitting exactly at the cutoff rank (`floor(n * (1 - cutoffPercent/100))` ranks-from-top, converted to an ascending index) — provably equivalent to `computeBandPercentiles`'s own ascending-index cutoff rule via `floor(n-x) = n-ceil(x)`, which is why **floor** (not round-half-up) was chosen: it keeps this consistent with the already-shipped percentile logic instead of introducing a second rounding convention. An out-of-range computed rank (extreme cutoff or a tiny pool) falls back to the top or bottom player. `hysteresis_mmr` is a fixed MMR-point buffer, **not** a percentile — it deliberately does **not** scale with `mmr_scale`/`mmr_shift` (that transform is display-only, see `getDisplayMMR()` in `config.ts`, and never feeds back into internal comparisons), so it always means the same 7 real MMR points regardless of display settings. `hysteresis_pct` is retired (migration `0028_hysteresis_mmr.sql`, same delete-from-a-later-migration pattern `0004_admin_roles.sql` used for `mod_role_id` — never edit the original seed migration). The promotion-vs-demotion decision itself (whether a player's percentile has dropped into a lower band at all, and which band they'd move to) is unchanged — still driven by `targetBandForPercentile`/percentile cutoffs; only the hysteresis buffer that gates whether a demotion candidate actually demotes switched from percentile-space to MMR-space.
  - **"Surpassed" bypass, added this session** (`computeBandChange`'s new `hasBeenSurpassed` param, `web/lib/discord/bands.ts`): grace and hysteresis both exist to absorb noise in a player's *own* recent results (one bad loss right after a promotion shouldn't immediately yank them back down) — they were never meant to indefinitely protect a player who stays static while *other* players' independent improvement climbs past them. Caught live: Luna sat at Garnet/847 MMR while Arya (882) and HeyItsNate (862) — both higher raw MMR — were correctly banded Iron, so the Info page's per-band "Currently N MMR" floor showed Iron above Garnet, which is structurally impossible when bands are correctly ordered. Root cause was confirmed to be grace/hysteresis, not a percentile-math bug — every other player's stored band matched their live percentile exactly; only Luna's was stale. **Fix**: `recomputeBands()` computes a `surpassedIds` set once per run, off a pre-loop snapshot of every player's currently-committed `band` (so the result can't depend on iteration order or a player's own band being rewritten mid-loop) — a player is "surpassed" if any other pool member has strictly higher MMR while currently holding a strictly lower band, which is only possible when a band assignment has already gone stale. `computeBandChange` bypasses grace and hysteresis entirely for a surpassed player (`targetIndex < currentIndex && (options?.force || hasBeenSurpassed)`, same immediate-demotion branch `force:true` already used) — a demotion not caused by being surpassed is unaffected and still goes through the normal grace-then-hysteresis checks exactly as before. This is stateless (no new columns, no MMR-delta-sign tracking, no per-recompute snapshots persisted) and self-limiting: it can only fire when a real ordering violation already exists, never during an ordinary noise dip where the player is still correctly ordered relative to the whole pool.
- On any band change: swap the player's Discord role, DM them the change.

**Placement bootstrap (revised this session — no longer a chicken-and-egg problem):** originally Rank Queue required `is_placed = true`, which only Rank Queue itself could earn toward (since only Rank Queue moves MMR and only games-played unlocks placement) — that circularity was resolved by routing brand-new players through Universal Queue first. That gate is now removed: a brand-new player can jump straight into Rank Queue and start earning MMR (starting at 0) from game one. They still show as unbanded (`NA` band/MMR on the leaderboard, excluded from the daily percentile pool) until `rank_games_played` crosses `placement_games_required`, at which point the next daily recompute assigns them a real band off whatever MMR they've accumulated by then. **Rank Queue games only** (revised this session — was `total_games_played`, counting both queues, until it was pointed out that placement assigns a band off MMR, and Universal Queue games never move MMR, so they shouldn't count toward earning one; the original both-queues counting was a holdover from the now-resolved chicken-and-egg bootstrap above, not a requirement of the current design). Universal Queue games still count toward `total_games_played` for other purposes (see "Queueing") — just not this gate.

**Band percentile cutoffs (decided this session via user question, not specified in the original spec):** the original docs establish the *concept* of percentile-based bands but never pin exact split points. Skewed toward the lower bands rather than equal quartiles, per the user's choice: cumulative cutoffs `band_cutoff_garnet_pctile=40`, `band_cutoff_emerald_pctile=70`, `band_cutoff_sapphire_pctile=90` (all admin-configurable) — Iron is below the 40th percentile, Garnet 40th-70th, Emerald 70th-90th, Sapphire 90th and above. **These are code defaults only** (`bands.ts`, `config.ts`'s `KNOWN_CONFIG_DEFAULTS`, `info/page.tsx`, `register-commands.mjs`) — the live Discord server currently has these overridden via `/admin config set` to an even 20/30/30/20 split (`band_cutoff_garnet_pctile=20`, `band_cutoff_emerald_pctile=50`, `band_cutoff_sapphire_pctile=80`), confirmed a later session by reverse-checking live leaderboard data (9 placed players) against both cutoff sets — 40/70/90 didn't match the observed bands at all, 20/50/80 matched all 9 exactly. Same DB-override-shadows-code-default caveat as `prism_top_n` (see "Bands / ranks" below) — if this ever needs to change, the code default and the live `/admin config set` value are two separate things to update.

**Implemented, Phase 5** (`web/lib/discord/bands.ts`, `web/app/api/discord/recompute-bands/route.ts`): `recomputeBands(options?: { force?: boolean })` is triggered daily by `pg_cron`/`pg_net` (migration `0009_schedule_bands_cron.sql`, `0 9 * * *`, reusing the same Vault secret and `x-sweep-secret` header convention as the existing sweep job — no need for a second secret since both are pg_net-triggered background jobs with the same trust boundary), over the whole pool. It pulls every non-test-data player who is either already placed or has just crossed `placement_games_required` on `rank_games_played` (Rank Queue games only — see "Placement bootstrap"), combines both groups into one MMR-sorted pool, sorts that pool by MMR (tied MMR broken by `total_games_played` descending — more games at the same rating is treated as a more established rank — then player id as a final deterministic tiebreak), and computes each player's percentile rank as `index / n * 100` before assigning bands off the cutoffs above (**revised a later session** — was `(index + 1) / n * 100`; the `+1` made the ladder 1-indexed, e.g. the lowest-MMR player sat at `1/n` rather than `0/n`, which shifted every rung up by one step and made the bottom cutoff harder to clear than the top cutoff at the same pool size — caught via a live 9-player example that split 1 Iron/2 Sapphire under a symmetric 20/80 cutoff instead of the expected 2/1; 0-indexing fixed it. Trade-off: a lone first-ever placed player is now trivially 0th percentile/Iron rather than 100th percentile/Sapphire — the opposite edge case from before, equally arbitrary for `n=1`, but self-corrects at the next recompute once the pool has more than one player, same as any other percentile edge case here). `report.ts` and `/admin unreport`/`correct-report` also call this same function after every Rank Queue settlement/correction. **Revised this session** — every caller now evaluates and writes the **full** currently-placed pool rather than a scoped `onlyPlayerIds` subset (removed): the earlier scoped version only ever re-examined a player's band on their *own* next report, which meant an early placer's band — computed against whatever tiny pool existed the moment they first crossed `placement_games_required` (the very first player to place is trivially 100th percentile, regardless of true skill) — could never be corrected by the pool growing around them unless they personally logged more Rank Queue games; in a small/growing community this reliably produced a skewed distribution (observed live: 5 placed players, 4 Sapphire/1 Garnet against cumulative cutoffs that should have spread them across all four bands). Now any settlement anywhere re-evaluates everyone, so a player can be corrected by someone *else's* game shifting the distribution, not just their own — grace/hysteresis still gate whether that re-evaluation actually becomes a demotion, per player, unchanged. Demotion applies grace first (`band_games_played < grace_games` is immune, short-circuiting before hysteresis is even checked) then hysteresis (only demote if the player's percentile is more than `hysteresis_pct` points below the *promotion-in threshold for their current band*, not the raw target-band cutoff — e.g. promoted into Sapphire at the 90th percentile, only demoted back out below the 85th at default settings). **`force:true`** (new this session, `/admin recompute-bands force:<bool>`, `computeBandChange`'s new `options?: { force?: boolean }` param) bypasses grace and hysteresis entirely for that one run, demoting straight to true current percentile — a one-time admin remedy for players already stuck at an inflated band from before this fix existed (who'd otherwise need to grind `grace_games` more Rank Queue games before the normal safeguards would even let a correction through); not intended for routine use, since grace/hysteresis exist specifically to damp game-to-game noise during ordinary play. `band_games_played` (new column, migration `0008_bands.sql`) resets to 0 on every band change (including a forced one) and increments alongside `rank_games_played` on every Rank Queue `/report` settlement (`report.ts`) — it's distinct from `rank_games_played` (lifetime Rank Queue count, powers provisional-K and now placement) and `total_games_played` (both queues, powers season eligibility and the tiebreak above, no longer placement). Role sync (`crl6mansqueuebot_band_roles`, admin-settable via `/setbandrole band:<Iron|Garnet|Emerald|Sapphire|Unranked> role:<@role>`, mirroring `/setqueuechannel`'s upsert pattern) removes the old band's role and grants the new one; on initial placement specifically, it also removes `Unranked` (granted back at first-ever queue — see "Bands / ranks" above) before granting the real band, so the role set always reflects exactly one current state rather than accumulating. Since the recompute has no Discord interaction to pull `guild_id` from (unlike every other bot code path), a new `getGuildId()` helper in `rest.ts` auto-detects it the same way `register-commands.mjs` already does (`GET /users/@me/guilds`, throws if the bot isn't in exactly 1 guild unless `DISCORD_GUILD_ID` is set), cached at module scope for warm-instance reuse. Band-change DMs reuse the existing best-effort `sendDirectMessage` helper. Test-data players (dev panel) are excluded from the whole pool — their fake `discord_id`s aren't real guild members (role sync would 404) and would distort real percentile cutoffs if mixed in.

**Grace-inactivity bypass, implemented this session** (`web/lib/discord/bands.ts`, `web/lib/discord/report.ts`, migration `0023_grace_inactivity.sql`): `players.last_rank_game_at timestamptz` is a new column, stamped `now()` on every Rank Queue `/report` settlement alongside the existing `rank_games_played`/`band_games_played` increments — it's the only thing on the row with a time dimension; every other placement/grace counter is a pure game-count that never decays on its own, which is exactly why an inactive-but-not-yet-demoted player could get stuck at an inflated band forever with no mechanism to re-examine them. `computeBandChange`'s demotion branch now checks `band_games_played >= graceGames` **or** inactivity past `graceInactivityDays` (config `grace_inactivity_days`, default `7`) before even considering hysteresis — either one is sufficient to unlock the hysteresis check, matching the two independent ways grace was already described as expiring (play enough games in the new band, or now: stop playing long enough). `graceInactivityDays <= 0` disables the check entirely (games-only grace, previous behavior). The migration backfills `last_rank_game_at` for every existing player from their most recent reported Rank Queue series (`series.reported_at`, joined through `series_players`), so this doesn't treat every already-active player as instantly stale on deploy. Not touched by `/admin unreport`/`correct-report` — an admin correcting or reversing a report doesn't retroactively un-set when the player last actually played, an accepted limitation matching this file's existing precedent for similar admin-tooling edge cases. `force:true` is unaffected — it already bypassed grace/hysteresis outright and doesn't consult this column.

**Live Prism, implemented this session** (`web/lib/discord/bands.ts`): supersedes the original season-end-only design — see the clarifying user exchange that drove this: *"being prism you just have to be the top #. Once a player reaches top # they get the prism role, if they fall out of it they lose it and go back to sapphire."* Implemented as a second pass inside `recomputeBands()`, run immediately after the 4-band percentile loop (same function, same trigger points — daily cron, every Rank Queue `/report` settlement, `/admin unreport`/`correct-report`/`recompute-bands`), not a separate scheduled job. Eligibility mirrors `top10_min_games`'s original season-close semantics but computed live: queries the currently-*active* season's `reported`, non-test-data, Rank Queue `series`/`series_players` rows to build a season-games-played count per player, then filters the (already band-assigned) pool to `is_placed && seasonGames >= top10_min_games`, sorts by MMR descending (tiebreak: season games played descending, then player id — same tiebreak philosophy as the daily band recompute and season-close standings), and takes the top `prism_top_n`. Deliberately **no grace period and no hysteresis** for Prism specifically — the user's requirement is a strict live cut, unlike ordinary demotion between the 4 real bands. `players.is_prism` is written directly here now (previously only `seasonClose.ts` wrote it); on grant, the player's real band role is removed and the `'Prism'` role (`crl6mansqueuebot_band_roles`) is granted, and vice versa on revoke — falling out of Prism needs no special "revert" logic since `player.band` (the real underlying band, almost always Sapphire) was never touched by the Prism pass, only role sync and `is_prism` were. `RecomputeSummary` gained `prismGranted`/`prismRevoked` counts, surfaced in `/admin recompute-bands`'s reply and audit-log entry alongside the existing promoted/demoted/unchanged counts. Season-boundary staleness (last season's Prism holders lingering after `/newseason` resets everyone's season-games count to 0) is handled by `seasons.ts` calling `recomputeBands()` once right after the new season opens — see "Seasons" below.

### Seasons
- Monthly, resets at the start of each calendar month.
- **Soft reset** — **the symmetric formula below is implemented but DISABLED (2026-08-31, same day, by user decision: _"Lets just put it back to mmr / 2. (Disable the change we just made, don't remove it)"_).** `SYMMETRIC_NEGATIVE_DECAY = false` in `web/lib/mmr/seasonDecay.ts` gates it; while false, `decayMmr` returns `mmr / 2` for `mmr < 0` and commit `814ee7c` stands unreversed. **Live behavior is therefore two-piece: `mmr / 2` below zero, the median-compression formula at and above zero.** The reason for reverting is the flagged consequence recorded below — symmetric decay recovers negatives *more slowly* than halving, which is precisely what `814ee7c` was meant to speed up. Deliberately a module constant, not a config key: it is a code-level choice of which formula is correct, and a config key would need a migration hand-applied before it could take effect. The `median <= 0` guard sits *outside* the flag and applies to both paths. Tests: `seasonClose.test.ts` asserts the halving as live behavior and keeps the two symmetric assertions in a `describe.skip("symmetric negative decay")` block to unskip alongside the flag. Everything from here down describes the **disabled** symmetric form, kept as the record of why it exists — a single continuous formula across the whole domain (supersedes the original linear median-compression formula, which could *increase* a below-median player's MMR; every player now strictly moves toward 0, and MMR can never cross zero as a result of decay):
  - `new_MMR = (mmr * median) / (median + decay_factor * |mmr|)` — a hyperbolic (Michaelis-Menten style) compression toward 0, scaled by the pool median.
  - **The `|mmr|` in the denominator is the 2026-08-31 revision** (`web/lib/mmr/seasonDecay.ts`), per direct user request: *"Could we apply our equation for soft reseting above the median for below the median as well."* It **supersedes the two-piece form**, whose below-zero half was a separate `mmr / 2` hack (itself having superseded `mmr / 3`). The user proposed feeding the formula `median - mmr` to keep its input positive; `|mmr|` is that idea computed against the pool's *actual* raw median, which on the live snapshot is **-0.54** — the pivot at 0 already **is** the median, so distance-from-zero is the right positive input. (Do not use `computeSafeMedian`'s return value as a pivot: it is `raw_median + shift`, a scale constant, not a location. Pivoting there would move the entire bottom half of the pool *upward* — a +20 player becoming +28 — which is inflation, not a reset.)
  - Writing it this way makes the function **odd**: `g(-x) === -g(x)`, so a player 30 below zero is pulled toward zero exactly as far as one 30 above. The old two-piece form had a **slope discontinuity at 0** (0.5 on the left, 1.0 on the right), so a player a hair below zero moved proportionally twice as far as one a hair above; that asymmetry is gone.
  - **Every positive-MMR result is bit-identical to the old formula** — for `mmr >= 0`, `|mmr| === mmr`. Only the below-zero half changed.
  - **Behavioral consequence, flagged to the user at the time**: every negative player recovers *more slowly* than under `/2`, since `|new| > |mmr/2|` exactly when `|mmr| < median/decay_factor` (≈106 live) and the pool floor is -53.5. Live: noah -53.47 → -35.53 (was -26.74); Mystic -20.06 → -16.86 (was -10.03); lux -0.54 → -0.54 (was -0.27). This runs *opposite* to commit `814ee7c` ("Halve negative MMR at season close instead of thirding it"), a deliberate earlier change to speed negative recovery — accepted knowingly, because `decay_factor` is now a **single lever on both halves of the pool** (it previously appeared only in the `mmr >= 0` branch and could not move a below-zero player at all). Faster negative recovery now costs harder top compression, and vice versa.
  - **`median <= 0` guard**: `decayMmr` returns `mmr` unchanged. Required, not defensive — `computeSafeMedian` can legitimately return 0 for a degenerate pool where at least half the players tie at the minimum (e.g. `[0, 0, 10]`, or `[-10, -10, 5]`), and without the guard every player collapses to 0 (and `0/0 = NaN` for one already at 0), silently wiping the pool. This also fixes that as a **pre-existing latent bug** in the two-piece form.
  - Properties (for `median > 0`): strictly increasing everywhere (`d/dx[xM/(M+fx)] = M²/(M+fx)² > 0`, and the odd extension inherits it), so decay never reorders players by MMR (same invariant the original formula had — see the decay-order note under "Implemented" below); sign-preserving and never crossing 0 (the denominator `M + f·|mmr|` is always positive); `decayMmr(0, ...)` exactly 0, so a never-played player is unaffected; bounded by `±median/decay_factor`, which is what compresses a runaway top (or bottom) far harder than the middle.
  - `decay_factor` default `0.25` (config), same key as before.
  - **Negative-median pole bug, fixed this session** (`web/lib/discord/seasonClose.ts`): the formula's safety claim above ("never crosses 0") only holds when `median > 0`. `applyMmrDecay` originally took a plain median of the whole `is_placed` pool's raw MMR — caught via a live example (`mmr_scale=7.25`, `mmr_shift=1000`) where more than half the placed pool sat below raw MMR 0 (their *display* MMR still looked like a normal positive range, purely because of the shift), so the plain median came out **negative** (-4.62). With a negative median, the denominator `median + decay_factor*mmr` hits a **pole at `mmr = -median/decay_factor`** (≈18.48 raw in that example): players near it got wildly amplified results (one player's raw MMR of 17.52 decayed to 335.33 — a ~19x blow-up), and the pool's single highest-MMR player (raw 91.03, past the pole) flipped to a *negative* decayed result, dropping below players who started beneath him — violating the "never reorders players" invariant this section already claimed. **Fix**: `computeSafeMedian()` shifts every pool value up by the pool's own minimum (so the lowest player sits at exactly 0) before taking the median, guaranteeing a non-negative scaling constant — the shift is used only to derive this one constant, `decayMmr` still runs on each player's real, unshifted `mmr`, so a below-zero player is compressed by their true distance from 0, not by a shifted stand-in. For a pool that's already all non-negative, the shift is 0 and this is identical to a plain median — no behavior change for a community that was never hitting the bug. Re-verified against the same live-data example that surfaced the bug (safe median 25.72 vs. the broken plain median -4.62): the pole disappears entirely, decay is now strictly non-decreasing in `mmr` end to end, and — coincidentally, with no `decay_factor` change needed — the pool's highest-MMR player now nets a plausible, non-extreme decay result under the unchanged default `decay_factor=0.25`, where before the fix he was the one landing below players who started under him. `decayMmr`/`computeSafeMedian` are exported and unit-tested (`web/lib/discord/seasonClose.test.ts`) against this exact regression case.
- **The soft-reset decay pool now covers unplaced players too (2026-08-31)** (`web/lib/discord/seasonClose.ts`'s `applyMmrDecay`; mirrored in `web/lib/mmr/reconstructMmrHistory.ts`'s `runDecayForSeason`). Supersedes every "decays every currently placed, non-test player" phrasing elsewhere in this file — the pool query dropped its `.eq("is_placed", true)` filter and is now just `is_test_data = false`. **Why**: unplaced players were carrying an un-decayed rating into a season where everyone else had been compressed, and because the two groups interleave across the whole ladder, an unplaced player could start the new season *above* a placed player they had finished below. The live pair that surfaced it: Murc (placed, raw 10.83) finished above Synthey (unplaced, raw 10.35) and, under the old pool, would have started the next season at 9.90 vs. Synthey's untouched 10.35. The formula's documented "strictly increasing, never reorders players" guarantee only ever held *within* the pool — it said nothing across the pool boundary, and the boundary was placement. Prompted by the user directly: *"Decay should effect unplaced players"*. **Free for the never-played case**: `decayMmr(0, median, f)` is exactly 0, so a player at raw 0 is unaffected by being included. **It does move the median**, though, which is the real behavioral change for everyone else — widening the pool from the placed subset to the whole roster shifts `computeSafeMedian`'s compression constant (on the live snapshot: 42 placed → 59 total, safe median 57.25 → 52.93), so every placed player decays slightly harder than before (1zen raw 116.3 → 55.4 rather than 57.7; display 1843 → 1402 rather than 1418). **Ordering consequence**: `resetAllPlacementsToUnranked()` still runs after `applyMmrDecay()`, but that ordering is no longer *required* by the decay — the old reason ("reset first and the decay pool comes back empty") is gone. It stays because the standings, `is_prism`, `is_placed` and `band_at_close` snapshots earlier in `closeSeason()` all have to read pre-reset values. - **All-time rating, added 2026-08-30** (`web/lib/mmr/allTimeRating.ts` + `allTimeRating.test.ts`, written by `seasonClose.ts`, migration `0048_season_score.sql`): a permanent cross-season career score, requested as something that "will live in the background and potentially be used in the future" — **nothing on the site or in Discord reads it yet**. Every closed season pays out points by final standing; a player's all-time rating is the sum of their `crl6mansqueuebot_season_history.season_score` rows across every season. Deliberately **not** a running total on the player row: season_history is already the permanent archive, so the career number stays re-derivable and a re-close or a corrected standing can't leave a denormalized counter wrong (same reasoning as `made_top10` becoming a snapshot, above).
  - **The curve** (user-supplied, `q = 0.25`), with `r` = 1-based placement and `N` = number of placed players that season: `b = (r-1)/(N/2-1)`, `k = 16.1045061696 * (38/(N-2))^q`, `a = 100*ln(100)/(k*(N/2-1))`, `score = 100^(1 - b/(a + (1-a)b))`. 1st place scores **exactly 100 at every field size** (b=0). `b = 1` exactly at `r = N/2`, where the score is exactly `100^0 = 1` — so the user's two stated rules ("bottom 50% earns nothing" and "below 1 earns nothing") are the *same* rule falling out of the curve, and **`r = N/2` is the last earning place, worth 1 point, not 0**. Past `b = 1` the expression has a pole (at `b = a/(a-1)`, for every N below ~70) and is never evaluated — the function returns 0 first. Larger fields pay more and reward depth: N=8 → 4 earners / ~203 total, N=12 → 6 / ~270, N=20 → 10 / ~375, N=40 → 20 / ~566 (and r=5 of 40 is exactly 50.0), N=100 → 50 / ~930. `N <= 2` divides by zero twice and simply pays nothing.
  - **`r` and `N` are placed-only, and re-ranked densely.** `season_rank` on the archive row covers *every* participant with ≥1 reported game, unplaced included; the score can't reuse it, since that would both inflate N and leave gaps in r wherever an unplaced player finished mid-table. `seasonScoresByPlayerId()` filters to `is_placed` and re-ranks 1..N inside that subset. Read at the same point in `closeSeason()` as the `is_prism` snapshot and for the same reason — `resetAllPlacementsToUnranked()` further down clears `is_placed`. Unplaced participants still get a history row, scoring 0.
  - **Migration `0048_season_score.sql` adds `season_score real not null default 0`** and is **not applied to production** — existing rows backfill to 0, so any season closed before it is applied has no recorded all-time points and nothing recomputes them. The test-data generator (`lib/test-data/generate.ts`) scores its synthetic standing with the same function; those rows are `is_test_data` and never reach a live career total.

### Self-service correction (`/correct`)
User's spec, verbatim intent: a mis-reported match should be player-fixable without needing an admin — 5 of the 6 participants running `/correct` flips the result "essentially the same way as `/admin correct-report`," each vote gets a basic progress embed with the match id and an N/5 tally, correction only ever applies to "their previously played match," and every reported match's embed should advertise that `/correct` exists.
- **Implemented** (`web/lib/discord/correct.ts`, migration `0045_correct_votes.sql`): `/correct` takes **zero options**, deliberately — rather than resolving a series from a channel or an `id:` override (the match channel and category are already deleted by the time a match is reportable, since `/report` tears them down immediately), it always resolves the caller's own most-recently-`reported`, non-test series via `series_players` (`order by reported_at desc limit 1`). This is what makes "they must all be a part of the match they want to correct" automatically true by construction — nobody can vote on a match unless it's specifically *their own* latest one, so two different players can only be voting on the same series if that series happens to be each of their latest reported match. If a participant has since played and reported a newer match, their `/correct` targets that newer one instead — they simply can't reach back to correct an older match anymore, an accepted consequence of "singular, latest match" rather than a match picker.
  - **Votes**: upsert into `crl6mansqueuebot_correct_votes` (PK `(series_id, player_id)`, "existence = pending" convention like `cancel_votes`/`abandon_votes`). Below 5, posts a `BRAND_COLOR` progress embed (`<@caller> wants to correct Match #N — count/5`) to the configured report channel plus an ephemeral confirmation — same per-vote-announcement shape `/cancel` uses (`registerCancelVoteAndMaybeVoid`/`processCancelCommand`, "Team formation (on pop)" above).
  - **One-time claim**: a dedicated `crl6mansqueuebot_series.correction_claimed_at` sentinel column (not a `status` transition — the series stays `'reported'` throughout, since `/report`'s and `/admin correct-report`/`unreport`'s own status handling must be unaffected) is claimed via the same `UPDATE...WHERE correction_claimed_at IS NULL` atomic pattern used everywhere else in this codebase. Once claimed, a match can never be corrected again via `/correct` — deliberate, to close off a flip-flop/griefing vector from repeated re-votes; an admin can still use `/admin correct-report` afterward if a genuine second mistake happens, since that path doesn't check this column at all.
  - **The flip itself** (`applyCorrection`) mirrors `adminTools.ts`'s `processCorrectReport` almost exactly — same "reverse the old per-player `mmr_delta`, apply a freshly-computed one" arithmetic, same `getConfigNumber` reads, same `effectiveKFactor` (`k_factor * bonus_day_multiplier * series_length_k_multiplier`), same win-streak-bonus recompute (excluding this series from `getPriorRankWinStreak` by id) and `recomputeBands()` call. The one place it goes further than the admin path: `/admin correct-report` posts no public message at all, but the whole point of `/correct` is giving the community a corrected result to look at, so `applyCorrection` also builds fresh Winners/Losers lines (same shape `report.ts`'s Rank Queue branch builds) and posts a brand-new embed via the exported `reportResultEmbed` (`report.ts`) to the report channel — a second, independent "Match Reported" message, not an edit of the original (which nobody kept a durable reference to). `series.winner_team` is flipped in the DB *before* any streak lookups run, which is safe only because `getPriorRankWinStreak`/`getPriorRankLossStreak` always exclude the series being scored by id regardless of its current DB winner — so the early flip doesn't skew "prior" streak math, and it's what lets the post-recompute `getStreakIds` call (used for the new embed's 🔥/🥶 decoration) see the corrected result as already-settled history, exactly as that helper's own doc comment expects.
  - **Advertisement footer**: every report embed (initial `/report` and any later `/correct`, both go through the same `reportResultEmbed`) ends with `-# Wrong result? Run /correct — 5 of the 6 players can flip it.` (Discord's `-#` subtext markdown), satisfying the "include at the bottom of every reported match" ask directly in the shared embed builder rather than duplicating copy at each call site.
  - **Not yet applied to production**: migration `0045_correct_votes.sql` (adds `crl6mansqueuebot_correct_votes` and `crl6mansqueuebot_series.correction_claimed_at`) needs the usual manual Supabase apply before `/correct` can be registered/used live.

### Admin toolset
- `/admin unreport`, `/admin cancel-series`, `/admin adjust-mmr`, `/admin force-leave`, `/admin recompute-bands`, `/admin config get|set`, `/admin audit-log`. (`/newseason` stays a standalone top-level command, not an `/admin` subcommand — see "Admin commands" below; the original spec's `/admin new-season` never got built as such.)
- All admin actions get a basic audit log entry (actor, action, target, details, timestamp).
- **`unreport`/`correct-report`'s `id:` accepts the report's Match # directly, fixed this session** (`resolveReportedSeriesId()`, `web/lib/discord/adminTools.ts`): both commands' `id:` param was always a strict `.eq("id", ...)` match against the series' raw UUID — but once match-number assignment moved to report time (migration `0042_match_number_on_report.sql`, see "`Match #N` voice-channel naming" above), the public report embed (`reportResultEmbed`, `report.ts`) is the *only* place a series' identity is ever shown to an admin, and it only ever shows `Match #N` (the `match_number`), never the UUID — so typing what's actually visible (e.g. `55`) into `id:` was guaranteed to fail with "That series isn't in a reported state or doesn't exist," reported live after an admin tried to correct Match #55. **Fixed**: a plain-digits `id:` input is now resolved against `match_number` first (scoped to `status='reported', is_test_data=false` — the only state either command ever targets, and the only state a match_number is ever assigned in), falling back to treating the input as a raw series UUID otherwise (e.g. one copied from the audit log) — an unresolvable digits-only input passes through unchanged so the existing "not reported / doesn't exist" error still fires correctly. Both Discord command option descriptions (`register-commands.mjs`) updated to say "The match number from the report (e.g. 55), or the series id." — this needs the Register Discord Commands workflow re-run to take effect (a description-only change, still requires re-registration same as any other command-shape edit).
- **Implemented** (`web/lib/discord/adminTools.ts`): four design questions were resolved before building — (1) `unreport` reverses a `'reported'` series to the existing `'void'` status rather than a new DB status, since the audit log entry already distinguishes an admin-corrected void from a genuine timeout/abandon void; the atomic claim is `UPDATE...WHERE status='reported'` (same claim pattern as everywhere else), and the unwind mirrors `report.ts`'s writes in reverse per `series_players` row — `total_games_played` always decrements, and for Rank Queue series `mmr -= mmr_delta`, `rank_games_played`, and `band_games_played` also decrement (each clamped at 0, in case a since-happened band change already reset `band_games_played`). A 6-mans series has 6 `series_players` rows, not 10 — an earlier draft of this bullet had the wrong count. **Revised this session**: both `correct-report` and `unreport` also call `recomputeBands()` (`bands.ts`) right after their own MMR writes (for `unreport`, gated on `series.queue_type === "rank"`, mirroring the `mmr`/`rank_games_played`/`band_games_played` unwind above it being similarly gated) — since either correcting a winner or reversing a report entirely can push someone across a band threshold, this keeps that reflected immediately rather than waiting for the next daily tick, mirroring `report.ts`'s live per-report recompute; each call now re-evaluates the full placed pool rather than just the series' 6 players, per the fix described under "Bands / ranks". (2) `adjust-mmr` takes a `target:<@user>` plus **either** `delta:` (relative) **or** `mmr:` (absolute), never both — validated as an XOR in application code, since the user wanted both input modes supported rather than picking one. (3) `force-leave target:<@user>` handles both possible states rather than assuming one: dequeues the player from any queue they're sitting in (reusing the now-exported `refreshQueueMessage` from `queue.ts`) *and* voids any series they're locked into (`series_lobby`/`series_players`, same lookup `isPlayerLockedInActiveSeries` uses but returning the full row) — an admin bypass for a stuck/unresponsive player when the other 5 can't gather the 3 `/abandon` votes. (4) `config get|set` validates its `key:` argument against `KNOWN_CONFIG_DEFAULTS` (`config.ts`), a hardcoded allowlist mirroring this file's own "Config values" table (and duplicated a third time as Discord command `choices` in `register-commands.mjs`, matching the existing duplication precedent `setbandrole`'s band choices already established) — `get` with no `key:` lists every known key with its current DB value or fallback default. `cancel-series [id]` and `force-leave`'s series-void case both reuse two helpers split out of what was one combined function in `matchChannels.ts`: `claimSeriesVoid()` (atomic claim + clear pending sub/abandon state + public closing message) and `closeMatchChannelsAfterDelay()` (the 30s wait + delete) — split apart specifically so the admin's ephemeral reply can fire right after the claim succeeds instead of blocking on the 30-second warning window, matching the reply-before-delay ordering `/report` and `/abandon` already use. `recompute-bands [force:<bool>]` is a thin wrapper around the existing `recomputeBands()` (`bands.ts`) — `force:true` bypasses grace/hysteresis for that run, see "Bands / ranks" for why that exists. Discord's `SUB_COMMAND_GROUP`/`SUB_COMMAND` nesting (needed for `config get`/`config set`) required a new `CommandOption` type (`types.ts`) supporting nested `options`, plus a small tree-walker (`resolveAdminSubcommandPath`) that tells a subcommand hop apart from a leaf param by whether `options` or `value` is present on the node.

**Admin change-log (added this session):** every admin action that changes persistent data now best-effort posts a Discord embed to an admin-configured logging channel, on top of the existing DB-only `crl6mansqueuebot_audit_log` row (unchanged — the embed is additive, not a replacement). `/setlogchannel [channel:]` (`web/lib/discord/queue.ts`, alongside the other channel-setter commands — infers the current channel if `channel:` is omitted, same pattern as `/setreportchannel`) stores the destination in `crl6mansqueuebot_config`'s `log_channel_id` key.
- **Implemented** (`web/lib/discord/admin.ts`): `logAdminAction(actorDiscordId, action, target?, details?, changes?, logChannelIdOverride?)` gained two new optional trailing params rather than a parallel function — every pre-existing call site (~25 of them, passing only `actorId`/`action`/`target?`/`details?`) keeps working unchanged and now additionally gets an embed for free once a log channel is configured. `changes?: ChangeEntry[]` (`{ field, before: string | null, after }`) is the structured before/after form; when a call site passes it instead of (or in addition to) `details`, `details` is derived from it (`field: before -> after`, joined with `;`) so `/admin audit-log`'s plain-text listing still shows something useful either way. `postChangeLogEmbed` builds one embed per call — an `Actor` field (`<@id>`), an optional `Target` field, then either up to 23 `changes` fields (Discord's 25-field-per-embed cap, minus Actor/Target) or a single `Details` field as a fallback — all field names/values truncated to Discord's 256/1024-char limits. Posting is wrapped in try/catch and never propagates: `logAdminAction` is awaited mid-flow by ~30 command handlers that must not fail their actual work over a logging embed failing (missing channel, bot lacking channel access, Discord API hiccup).
- **Which call sites got structured `changes` vs. stayed action-style** (`details`-only, still produces a usable embed via the fallback): config-value setters (`config set`, `bonus-day toggle`/`set-bonus`/`set-day`, `streak-bonus toggle`, `queue-message-mode`, `setguildid`, `stop`/`start`, `set-rank-emoji`, `adjust-mmr`, `/setqueuechannel`, `/set6manscallcategory`, `/setreportchannel`, `/setlogchannel` itself, `/setqueuementionrole`, `/setmentionrole`, `/setbandrole`, `/setnotificationrole`) all fetch the prior value before writing and pass a one-entry (or few-entry) `changes` array. `recompute-bands`, `unreport`, `correct-report`, `cancel-series`, `cancel-matches`, `force-leave`, `reset`, `full-reset`, `test-flow`, `/setnotificationchannel` were deliberately left on the plain `details` string — these are action-oriented (a whole series voided, a whole pool recomputed, a message posted to a channel) rather than single-variable before/after edits, and listing e.g. every player's band change from one `recompute-bands` run would blow past the 25-field cap anyway; the `details` summary they already had is what the embed shows instead, satisfying the "if possible" qualifier without overengineering the cases where "before/after" doesn't cleanly apply.
- **`logChannelIdOverride`** exists solely for `/admin reset` and `/admin full-reset`: `full-reset` deletes `crl6mansqueuebot_config` (and thus `log_channel_id`) as part of what it's logging, so both handlers read `log_channel_id` *before* the wipe and pass it through explicitly — otherwise the action that destroys the log channel's own configuration would have nothing to post itself to.

## Discord bot commands & channels (resolved design, Phase 2 implementation starting)

Design discussion held this session, ahead of Phase 2 (queue system) implementation. This section originally described a button-driven queue UI, revised at the time in favor of buttons over slash commands to avoid channel spam. **Superseded in a later session**: queueing moved back to slash commands (`/q`/`/queue`, `/l`/`/leave`) so queue channels can stay plain text channels, using a delete-and-repost single-message pattern instead of buttons to still avoid clutter — see "Queue channels" below for the current design. The private-per-match-channel piece of the original design (for report/sub/abandon's implicit series context) is unchanged.

### Discord bot runtime architecture (decided this session)
- The bot is a Next.js API route, `web/app/api/discord/interactions/route.ts`, registered with Discord as the application's **Interactions Endpoint URL**. No `discord.js` `Client`/gateway connection, no privileged gateway intents (Server Members Intent etc. are gateway-only concepts and not needed) — member data arrives directly in the interaction payload.
- **Signature verification**: Discord signs every request with Ed25519; the route reads the **raw request body** (`await req.text()`, not `req.json()`) and verifies it with the `discord-interactions` package and the app's **Public Key** *before* parsing JSON — verifying after parsing is a known intermittent-failure trap. Unsigned/invalid requests get rejected; a bare `PING` gets an immediate `PONG` (Discord requires this to accept the endpoint URL when it's first registered).
- **3-second response limit**: Discord requires a response within 3 seconds, which heavier handlers (e.g. pop → create a category + 1 text channel + permission overwrites) can't reliably hit, especially through a cold start. Pattern: reply immediately with a **deferred ACK** (type 5, "thinking…"), then do the real work and edit the original response afterward via bot-token REST. Because a serverless function can freeze the instant it returns, the follow-up work is wrapped in **`waitUntil`** (`@vercel/functions`) so it keeps running after the ACK is sent — this round-trip needs to be verified working in production before the pop handler is built on top of it (see Phase 2 implementation tasks).
- **Queue status message updates** use bot-token REST, not interaction webhook tokens (those expire after 15 minutes and can't be used for later edits from an unrelated future join). **Revised in a later session**: rather than `PATCH`-editing one message in place, each join/leave now deletes the previously tracked message for that channel and posts a fresh one (`postFreshQueueMessage`, `queue.ts`), keeping exactly one live queue-status message per channel at all times — see "Queue channels" below. The channel→message ID mapping is still stored in the DB (`crl6mansqueuebot_queue_messages`) so the bot can find and delete the right message across restarts.
- **A long debugging session chased "newly-registered commands don't appear in the Discord client" (`/admin series-length-vote`, `/profile`, a throwaway `/test-button`) without ever finding a code-level cause** — every theory (response-type enums, malformed response bodies, module-init failures, Vercel/Supabase region latency) was directly disproven, several via local simulation of signed interactions against the route handler. Setting `DISCORD_GUILD_ID` as a GitHub Actions secret (previously unset, relying on the script's single-guild auto-detect) was tried and *appeared* to fix it. **It didn't, and this is worth recording precisely so it isn't repeated**: comparing the workflow run immediately before that change against the one after showed both had already auto-detected the correct single guild (`CRL West 6 Mans`) and registered the identical full command list, including the commands that supposedly weren't appearing — proven directly from Discord's own API response, not inferred. There was no failed run in between either. The two runs were functionally identical; the variable changed nothing observable. The most likely real explanation is mundane: sheer Discord client-side propagation delay, plausibly worse than usual given this session ran nine back-to-back registrations in a short window. `register-commands.mjs` still unconditionally logs which guild it targets and whether that came from `DISCORD_GUILD_ID` or auto-detection — worth keeping regardless, since it makes the target auditable rather than inferred — but **do not cite the missing secret as the root cause of a future "commands don't appear" report**; check the actual pre/post workflow logs the way this entry describes before concluding a fix worked.
- **Background sweeps** (series timeout, vote timeout, sub-request timeout) have no interaction to hang off of, so they're driven by **Supabase `pg_cron` + `pg_net`**, calling a secret-guarded sweep API route on a `* * * * *` (every-minute) schedule — plenty of precision for timeouts measured in minutes/hours. This was chosen over Vercel Cron specifically to avoid depending on Vercel's cron-tier limits, since Supabase is already provisioned for this project.
- **Command latency, addressed this session**: a live latency question ("how quickly should `/q` respond?") surfaced that the visible result — the queue message actually updating, not just Discord's "thinking…" deferred ack, which was already near-instant — was taking noticeably longer than it should, largely from `config.ts`'s `getConfigValue()` doing a fresh, uncached Supabase round trip on *every single call*, with a typical `/q` reading 6+ config keys across `bonusDay.ts`/`richEventEmbed`/etc. Also flagged, separately: Vercel's Function region and the Supabase project's region were mismatched (West vs. East) — a coast-to-coast round trip penalty on every one of those DB calls, likely the single largest contributor, but that's an infrastructure setting outside this codebase to fix (Vercel Dashboard → Settings → Functions → Function Region), not something addressed in code.
  - **Config table caching** (`web/lib/discord/config.ts`): the whole `crl6mansqueuebot_config` table is now cached in a module-scope `Map`, loaded once per warm instance and refreshed on a 30s TTL (`CONFIG_CACHE_TTL_MS`) — collapsing concurrent cache-miss callers onto one in-flight fetch (`configCacheLoadPromise`) rather than each firing its own `SELECT`. `setConfigValue`/`deleteConfigValue` also update the in-memory cache immediately, so the instance that handled an admin's own config-writing command sees the change on its very next read rather than waiting out the TTL — other already-warm instances still only pick it up once their own cache expires, an accepted tradeoff given config changes are rare and admin-only. This benefits every command that reads config, not just queueing.
  - **Eliminated a redundant DB round trip on every `/q`/`/l`** (`web/lib/discord/queue.ts`): `processQueueCommand` already looks up the channel's `crl6mansqueuebot_queue_messages` row (to resolve channel→queue_type) before doing anything else — `refreshQueueMessage` was then re-querying that *exact same row* moments later (by `queue_type` instead of `channel_id`, but same single-row-per-queue-type table) to get `channel_id`/`message_id`. `refreshQueueMessage` gained an optional `knownMsgRow` param, used only for the retry loop's first attempt — if the optimistic claim built off it loses the race (another refresh already moved `message_id`), attempt 2 falls back to a fresh fetch exactly as before, so a slightly stale known row is never unsafe, just occasionally not the fast path. `processQueueCommand`'s initial lookup was widened from `select("queue_type")` to `select("*")` to have `channel_id`/`message_id` on hand to pass through. Applies to every mode (simplified/default/hybrid/rich) uniformly, since it's in the shared join/leave path, not anything rich-mode-specific.
  - **Parallelized remaining sequential config reads** (`bonusDay.ts`'s `computeBonusDayMultiplier`, `queue.ts`'s `richEventEmbed`) with `Promise.all` instead of sequential awaits — a smaller win now that the config cache means the underlying round trip cost no longer scales with how many individual keys are requested (the whole table is fetched once regardless), but still cuts a few sequential microtask ticks off every queue event.

### Queue channels
- **`#universal-queue`** — open to everyone, no role gate.
- **`#rank-queue`** — single shared channel, **open to everyone with no role gate** (revised — the `Unranked` role no longer restricts access, see "Bands / ranks" above); the bot pools all joins together with no band segregation in matchmaking.
- **Slash commands, not buttons** (revised in a later session — queue channels stay plain text channels): `/q` or `/queue` to join, `/l` or `/leave` to leave, all channel-inferred (the bot looks up which queue a channel maps to via `crl6mansqueuebot_queue_messages`, populated by `/setqueuechannel`). Discord has no native command-aliasing, so `/q`/`/queue` and `/l`/`/leave` are 4 separately registered commands that resolve to the same two handlers.
- Each queue channel has exactly one **live queue-status message** showing the current member list. Instead of editing a message in place, every join/leave **deletes the previous tracked message and posts a fresh one** (`postFreshQueueMessage`, `web/lib/discord/queue.ts`) — chosen so the queue status always appears as the newest message in the channel (a plain text channel has ordinary chat happening in it too, unlike the old buttons-only design), while still keeping exactly one live status message and avoiding clutter. **Added this session**: the 6th join that pops the queue now also shows this same status refresh at 6/6 (the "`<@user> has joined...`" treatment, same as any other join) before `handlePop` clears the members and the vote/draft embed becomes the channel's newest message — previously the queue jumped straight from 5/6 to the vote message with no visible 6/6 state.
- **`/admin queue-message-mode mode:<simplified|default|hybrid|rich>`** (config key `queue_message_mode`, default `simplified` — supersedes an earlier boolean `/admin simplify-queue-messages enabled:<bool>`/`queue_simplified_messages` toggle this session, which `getQueueMessageMode()` still reads as a fallback if the new string key was never set, so an admin's prior choice keeps working unmigrated): four modes for how join/leave messages behave in a queue channel, implemented as a dedicated choice-validated command rather than the generic `/admin config set` (same precedent as `bot_paused`'s `/admin stop`/`/admin start` and `bonus_day_enabled`'s `/admin bonus-day toggle`).
  - **`simplified`** (default): exactly one live status message per channel, as above — every join/leave deletes the previous one and posts a fresh combined headline+roster message.
  - **`default`**: every join/leave posts a new combined headline+roster message without deleting the previous one, so the channel keeps a running history instead of pruning down to a single live message.
  - **`hybrid`** (added this session, `web/lib/discord/queue.ts`): every join/leave posts **two** separate messages instead of one combined message — (1) a small headline-only announcement embed (e.g. "`<@user> has joined the Rank Queue!`"), posted via `postHybridAnnouncement` and **never tracked or deleted**, so it stacks as a running join/leave log; and (2) a roster message (`hybridRosterEmbed`) listing every current member **one per line** — rank emoji (`getRankEmoji`), `@mention` (with 🔥/🥶 streak decoration same as everywhere else), band label, and display-transformed MMR — rather than the flat space-separated `@mention @mention...` line the other two modes use. The roster message behaves like `simplified` (single live message, delete-and-repost) with one deliberate exception: **the roster posted at the moment a queue pops (6th join) is frozen permanently** instead of being replaced/deleted by the next queue cycle, so it stays visible as a record of who played that match even after it's reported and more queues cycle through. Implemented via `freezeQueueRosterMessage`: right after that final roster post, its tracking is moved out of `crl6mansqueuebot_queue_messages` (the single-row-per-queue-type table every subsequent refresh reads/deletes from) and into `crl6mansqueuebot_queue_channel_messages`'s existing `keep_permanently` flag (the same mechanism `finalizeTeams`'s "Teams formed!" message already uses in `teamFormation.ts`), then the `queue_messages` row's `message_id` is set to `null` (kept, not deleted) so the next cycle's first join starts a brand-new tracked message from scratch instead of trying to delete the now-permanent one. **Revised a later session**: this used to immediately repost a fresh, empty "Current Queue Members: 0" placeholder message right after re-homing the frozen one — the row's `message_id` column was `not null`, and `processQueueCommand` (`/q`/`/l`) resolves a channel's queue_type off this exact table with no fallback for a missing row, so *something* had to keep the row populated. Reported live as unnecessary noise ("Is it possible you can remove it because it is not necessary") — the placeholder added a visible, contentless message to the channel on every single pop for no reason a player could use. **Fixed** by dropping the `not null` constraint (migration `0044_nullable_queue_message_id.sql`) so the row can exist with `message_id: null`, meaning "this queue_type is mapped to this channel, but nothing is currently posted." `tryPostAndClaimQueueMessage`'s CAS claim (used by every join/leave refresh, `refreshQueueMessage`) was generalized to accept a `null` `oldMessageId`, claiming via `.is("message_id", null)` instead of `.eq("message_id", oldMessageId)` in that case, and skipping the now-nonexistent "delete the old message" step — so the very next join after a pop claims the null row directly and posts the real join card as its first message, with no placeholder ever shown in between.
  - **`rich`** (added a later session, `web/lib/discord/queue.ts`, born from a Discord-mockup Artifact the user approved with "this looks amazing! go ahead and implement it"): the announcement embed (`richEventEmbed`) is data-rich rather than a plain headline, showing rank/MMR/streak plus a full-width `Queue Progress` field rendering a 6-segment block bar. Colors are Discord-native green (`RICH_JOIN_COLOR = 0x3ba55d`) / red (`RICH_LEAVE_COLOR = 0xed4245`) for join vs. leave, both overridden by the existing `SUPERCHARGED_COLOR` on a bonus day — same precedent every other queue-status embed already follows. Applies uniformly to both queue types with no special-casing: a Universal Queue player's streak text simply never appears, since it's driven by Rank-Queue-only streak counts that are always 0 for them. No avatar thumbnail — `DiscordInteraction`/`DiscordUser` carry no avatar hash and this codebase has no CDN URL-building helper, so that part of the original mockup was dropped from scope rather than built (**superseded a later session** — see below, once `players.avatar_url` existed for the website's Match History cards, the same missing piece this note cites).
    - **Collapsed to one message per event, revised a later session** — supersedes the original two-message shape (an always-stacking announcement plus a *separate*, tracked delete-and-repost roster message mirroring hybrid's shape): with `/status` already available on demand for "see the whole current roster," the second roster message was redundant, per direct user request ("I would only like the one message to be sent since players already have the option to run the status command to see the whole queue"). `richEventEmbed`'s single embed is now posted **"default"-style** — a new message per join/leave, nothing deleted, so the channel keeps a running history — rather than hybrid's tracked/delete-and-repost pattern; `tryPostAndClaimQueueMessage`'s old-message-deletion check changed from `mode !== "default"` to `mode !== "default" && mode !== "rich"` to match. `postRichAnnouncement` (the old separate-announcement poster) was deleted as dead code.
    - **Layout tightened, revised a later session** — supersedes the original Markdown `###` H3 headline (`### <name> joined/left the ... Queue!` — itself already condensed from an initial H1/`#` per earlier feedback that it rendered too large) plus three separate inline `Rank`/`MMR`/`Streak` embed fields. Caught via a live screenshot: Discord's client adds real top margin above a heading-led description, and stacks "inline" fields vertically once the embed narrows (routine on mobile), so the card had a large empty gap under its colored border and Rank/MMR/Streak spread across several full-width rows instead of reading as one line. Fixed by dropping the heading entirely for plain `**bold**` text (no built-in heading margin) and collapsing Rank/MMR/Streak into a single line directly under it, in the embed's `description` rather than separate `fields` (no per-field padding between them). The rank is now the same custom rank emoji (`getRankEmoji`) every roster line already uses, replacing the plain-text band name (`getRankLabel`) entirely, per direct request ("instead of a word for the ranks... use the actual ranks emoji"). `Queue Progress` stays its own field (the one remaining `fields` entry) — and its filled-segment emoji swaps to 🟪 on a Bonus Range day instead of always 🟩, matching the embed's own `SUPERCHARGED_COLOR` border rather than staying green while everything else around it goes purple.
    - **Streak suffix format, revised a later session** — supersedes the original `· 🔥 N-Win Streak` / `· 🥶 N-Loss Streak` middle-dot suffix (which the reporting test player simply wasn't on a long enough streak to ever surface, reading as "the streak doesn't show at all"), per explicit requested format: `${displayMmr} MMR   |   +${winStreak} Win Streak🔥` for a win streak, `${displayMmr} MMR   |   ${lossStreak} Loss Streak🥶` for a loss streak — a `|`-separated block instead of a middle dot, the emoji moved to the end of the phrase instead of the front, and a `+` prefix on the win-streak count only (a loss streak isn't a "gain," so it stays unprefixed). Pulls `ON_FIRE_EMOJI`/`COLD_EMOJI` from `streaks.ts` rather than a hardcoded literal, so it's guaranteed to be the exact same 🔥/🥶 used everywhere else in the bot (mention decoration, leaderboard) instead of risking drift.
    - **Pop (6th join) shows the ordinary per-player join card — reverted a later session, supersedes the intervening "roster copy instead of a join card" design.** That intervening design (Pop showed a copy of the status message in place of the ordinary join card, with the dedicated gold "Match Found!" announcement staying as a separate message alongside it) was itself already a correction of an even earlier version that went further and replaced the Match Found announcement too. ### Voice channels (created per series on pop, in admin-specified category)
- On pop, the bot creates **two voice channels** in the admin-specified 6-mans call category (set via `/set6manscallcategory`), one per team, named after the teams.
- **Viewable by anyone, joinable only by the team** (revised this session, per community feedback — supersedes the original "visible only to the 6 players" design): `createVoiceChannels` (`web/lib/discord/queue.ts`) sets `@everyone`'s per-channel overwrite to `allow: VIEW_CHANNEL, deny: CONNECT`, so the whole server can see which games are live and who's in them, but only the 6 participants, admin-role holders, and the bot get a member/role-level `allow: VIEW_CHANNEL | CONNECT` overwrite — Discord resolves `@everyone` first and member/role-specific overwrites take precedence over it, so those explicit allows override the `@everyone` CONNECT deny for exactly the people who should be able to join. Admin-role holders also get visibility via a **category-level** permission overwrite on the admin-specified category (cascades to all child channels with no extra per-channel step) — this is now redundant with the public `@everyone` VIEW_CHANNEL grant for viewing, but still relevant for anything else category-level access covers. `/sub`'s accept flow (`web/lib/discord/sub.ts`) already composed cleanly with this without any change: it grants the incoming substitute a member-level `VIEW_CHANNEL | CONNECT` overwrite and deletes the leaving player's member-level overwrite entirely (rather than denying it) — once deleted, the leaving player falls back to the `@everyone` overwrite, which is exactly the desired "can still view, can no longer join" state.
- `/report`, `/sub`, `/nominate`, `/abandon` are slash commands with no channel-inference requirement — players run them from anywhere (though `/sub`, `/nominate`, and `/abandon` typically run from queue channels for convenience). `/report` requires the player to specify `result:<win|loss>` to indicate their team's outcome.
- **Series end** (report settles it, abandon-vote passes, `series_timeout_hours` elapses, or admin `/admin cancel-series`) → voice channels are **deleted instantly** (no delay) → all 6 players unlocked to queue again.
- **Post-match lobby redirect** (added this session, `/setlobbychannel channel:<#voice>`, config `lobby_voice_channel_id`): deleting a team voice channel drops whoever's still in it out of voice entirely; instead, the 6 participants are **moved into a configured lobby voice channel** first. **Implemented** as `moveTeamVoiceOccupantsToLobby` (`web/lib/discord/matchChannels.ts`), called at the top of `deleteMatchChannels` — *before* the delete loop, since once a channel is gone there's nobody left in it to move. Hooking the shared teardown rather than `/report` specifically means this covers **every** end path with no per-call-site flag: report, `/cancel`, `/abandon`, the 2-hour timeout sweep, `/admin cancel-series`/`force-leave`, and test-match teardown. **Scoped exactly like `/sub`'s team-channel handling**: a player is moved only if their *current* voice channel is one of **that series' own two team channels** — anyone sitting in an unrelated call, or in no call, is left alone (explicit user requirement, stated twice). Discord has no REST endpoint listing a voice channel's occupants, so each participant's own state is read via `GET /guilds/{id}/voice-states/{user_id}` and moved with `PATCH /guilds/{id}/members/{user_id} {channel_id}` — note this is the same guild-wide member-move API whose *unguarded* use in `/sub` caused the "kicked out of their call no matter what call they are in" regression (see "Substitutes"), which is why the current-channel check here is a hard precondition rather than a nicety. Best-effort end to end (each lookup/move individually caught, the whole call wrapped again at the `deleteMatchChannels` call site) — a redirect failure must never block teardown. Test-data players are skipped (no real account to move), and an **unconfigured `lobby_voice_channel_id` is a clean no-op** that leaves the prior disconnect-on-delete behavior exactly as it was. Requires the bot to hold **Move Members**, and players to be able to connect to the destination; `/setlobbychannel`'s confirmation reply says both. The command itself mirrors `/setlogchannel`'s handler shape (admin-gated, ephemeral defer, config upsert, structured `changes` audit entry) with one difference: its `channel:` option is **required** and restricted to `channel_types: [2, 13]` (voice/stage), since the infer-the-current-channel fallback the text-channel setters use makes no sense for a voice destination.
- The existing 2-hour timeout sweep also checks for and cleans up **orphaned voice channels** (e.g. left behind by a bot crash/restart mid-series) in addition to force-cancelling the DB series record. **Implemented, Phase 4/6**: this backstop now also covers *reported* series — `/report`'s own instant deletion is a single in-function attempt with no retry, so the per-minute sweep additionally re-checks any series with `status='reported'` and `reported_at` more than 60 seconds ago that still has non-null voice-channel ids, and deletes+nulls them. This is belt-and-suspenders: normal reports are cleaned up by `/report` itself well before the sweep would ever see them.
- **`Match #N` voice-channel naming, and the `match_number` race that broke it — fixed this session** (`web/lib/discord/queue.ts`, `web/lib/discord/report.ts`, migration `0030_fix_match_number_race.sql`): `createVoiceChannels` names each series' two voice channels `Team Blue - Match #<N>` / `Team Orange - Match #<N>` off `crl6mansqueuebot_series.match_number`, falling back to `seriesId.slice(0, 7)` when it's `null`. That fallback was firing on nearly every match — reported by the user as "it falls back to the first 7 characters of the series every time." Root cause: `match_number` (an `integer unique` column added in migration `0016_series_match_number.sql` with no default/sequence behind it) had **two independent, uncoordinated writers**, neither error-checked: `handlePop` (`queue.ts`) assigned "count of already-`reported` series" at pop time, and `/report` (`report.ts`) separately recomputed a different "count of reported series" value and overwrote the same column at report time. Since matches normally stay `forming`/`active` for a while before anyone reports, more than one series is almost always in-flight at once, so the pop-time count is identical across them — every pop after the very first match ever played collided with the column's `UNIQUE` constraint, the failed `UPDATE`'s error was silently swallowed, and `match_number` stayed `null`, which is exactly what `teamFormation.ts` then read back for `createVoiceChannels`. **Fixed** by removing both hand-rolled assignments entirely and backing the column with a real Postgres sequence (`crl6mansqueuebot_match_number_seq`) via a column default, so a value is assigned atomically at series-`INSERT` time (pop) with no possible collision — `report.ts` no longer maintains a second, conflicting numbering scheme; it just reads the already-assigned `series.match_number` for its report-channel embed's `encodeMatchId()` match ID (see `web/lib/discord/matchId.ts` — plain decimal digits, `0`-`9`, revised a later session down from an intermediate base-36 alphabet (digits + lowercase letters), which itself had earlier superseded an original base-71 alphabet that also used uppercase letters and symbol characters; previously undocumented here). `match_number: number | null` was also added to `SeriesRow` (`web/lib/supabase/types.ts`), removing the `as any` casts this bug's workarounds had accumulated in `adminTools.ts` (`/admin unreport`/`correct-report`'s "Match #N" reply labels). **Migration `0030` needs to be applied to the production Supabase project manually** — same as `0029` before it, this sandbox has no DB write access.
  - **Sequence desync, fixed a later session** (migration `0034_resync_match_number_seq.sql`): `0030`'s `setval()` only synced the sequence past whatever `match_number` values existed at the moment it ran — a row that later gets a `match_number` some other way (a manual edit/restore via Supabase's Table Editor, not through `handlePop`'s plain insert, which never sets this column itself) can leave the sequence pointing below the table's real max. Hit live: `duplicate key value violates unique constraint... Key (match_number)=(18) already exists` with matches up to #27 already existing while the sequence was still only counting up to 18. Fix is the same `setval()` idiom re-run to catch the sequence up past the current max — no application-code change, since `handlePop`/`report.ts` were already correct (they never write this column). **Needs manual production application, same as every other migration from this sandbox.**
  - **Test matches and dev-panel synthetic data were also consuming the sequence, fixed a later session** (migration `0041_close_match_number_gaps.sql`): the column default fires on *any* insert that omits `match_number`, and neither `/test-rank-match`/`/test-universal-match` (`testMatch.ts`) nor the `/dev` panel's bulk generator (`lib/test-data/generate.ts`) — the only other two insert sites into `crl6mansqueuebot_series`, confirmed by grepping every insert into the table — excluded themselves from it, despite being `is_test_data = true`. Reported live as real match numbers jumping straight from #10 to #17. **Fixed**: both sites now explicitly write `match_number: null` on insert, which overrides the column default entirely (Postgres only applies a column default when the column is *omitted*, not when explicitly set to `null`) — a test series just gets no match number, falling back to the pre-existing `seriesId.slice(0, 7)` voice-channel naming exactly like any other `null` case. The migration is the one-time cleanup for rows that already have the gaps: renumbers every non-test series with a `match_number` to consecutive integers in their existing relative order (a real match's position relative to other real matches was never wrong, only the absolute numbers, since the sequence is monotonic regardless of who claims each value), nulls out every test row's `match_number`, and resyncs the sequence. Renumbering under the column's `UNIQUE` constraint needs two passes — the target consecutive range overlaps the existing range (e.g. old `{1,2,3,6,7,9}` → new `{1,2,3,4,5,6}`), so a single `UPDATE` can try to write a value that collides with another row's not-yet-updated old value depending on row processing order; moving everything to a disjoint negative range first, then flipping to the final positive values, avoids that entirely since `match_number` has only ever held positive values. **Needs manual production application, same as every other migration from this sandbox.**
  - **Void/cancelled matches were still consuming real numbers, fixed a later session** (migration `0042_match_number_on_report.sql`): `0041` only fixed test data — every real (non-test) pop still assigned a `match_number` via the column default, including matches that were later cancelled, abandoned, or timed out, since nothing at pop time knows a series' eventual outcome. Reported live after `0041`: the user counted 52 actually-reported matches, but the sequence had continued from 62 — the extra 10 were void/cancelled real series numbered right alongside the reported ones. **Fixed** by moving assignment from pop time to report time entirely: the column default is dropped (`alter column match_number drop default`), and a new stored function, `crl6mansqueuebot_assign_match_number(p_series_id)`, atomically assigns the next sequence value at the exact moment a series settles to `'reported'` — called from `report.ts` right after the existing atomic status claim, gated on `!series.is_test_data` so test matches still never get a real number. A stored function (not a plain read-`nextval()`-then-write in application code) is what keeps the assignment atomic under concurrent reports, same reasoning as `crl6mansqueuebot_join_queue` (`0002_queue_system.sql`). The migration also does the one-time cleanup: renumbers every already-`reported`, non-test series to consecutive integers in `reported_at` order (matching the new assignment semantic exactly), and nulls out `match_number` for everything else — void, cancelled, still in-flight, or test. Same two-pass negate trick as `0041` for the renumber itself.
    - **Voice channels lose their live match number as a result — replaced with a "preview," not a regression that went unaddressed**: `createVoiceChannels` names channels at team-formation time, well before any match is reported, so a real `match_number` genuinely doesn't exist yet at that point under the new scheme. Per explicit request ("you can still include the number... it just requires adding 1 from the most recent match since it's linear — account for multiple matches going on at once"), `teamFormation.ts`'s `computePreviewMatchNumber()` estimates it: the count of already-reported real matches, plus how many *other* currently in-flight (`forming`/`active`, non-test) real matches were created at or before this one. That second term is what makes several concurrent matches each get a distinct, increasing preview instead of all of them showing the same "current max + 1" — but since matches don't necessarily *report* in the order they were created, a given match's preview can still end up different from its actual final `match_number` once it reports. Display-only, computed fresh on every call, never persisted or reconciled — there's nothing to keep in sync when that happens, by design.
    - **Test matches and the `/dev` panel generator no longer need to explicitly null `match_number`**: `0041`'s fix (both sites explicitly writing `match_number: null` to override the column default) became unnecessary once `0042` dropped that default entirely — an insert that omits the column now gets `null` regardless of `is_test_data`, so those explicit writes (and their now-stale comments referencing "the column default") were removed from `testMatch.ts`/`lib/test-data/generate.ts` in the same pass.

### Team formation (voting in queue channel, drafting via DM)
- Bot posts a **vote message with two buttons** (Balanced / Captains) in the queue channel. First option to reach 3 of 6 votes wins; a 3-3 tie resolves to Captains (unchanged). Players' `/vote-default` preference auto-casts but is still overridable per game — players can click the other button to switch their vote.
- **Total vote silence** (nobody votes within `vote_timeout_seconds`) → **cancel the series** (void, same as an unreported timeout) rather than defaulting to a mode — decided this session.
- **Captains mode**: two of the top three players by MMR become captains, chosen at random (see "Team formation (on pop)" under Game mechanics for the canonical rule — revised this session, was strictly the top two). Draft order: **Captain 1 picks one player → Captain 2 picks two players → the last remaining player auto-assigns to Captain 1's team**. Pick prompts are DMed to whichever captain currently has the turn (`sendDirectMessage` with a `components` param, `web/lib/discord/teamFormation.ts`'s `sendDraftPickPrompt`) — no slash command needed, captains just interact with the prompt in DMs. Discord's platform does not allow a bot to force-open a DM to a user who has DMs closed to non-friends/bots — this is a hard API limitation with no workaround, so on DM-send failure the bot falls back to posting the same prompt directly in the queue channel with a status line @-mentioning the captain and explaining their DMs are closed. Since a DM-originated interaction carries no `guild_id` of its own, pick resolution uses `interaction.guild_id ?? (await getGuildId())`, reusing the same guild-auto-detection helper background jobs (e.g. the daily band recompute) already use.
  - **Revised this session**: Captain 1's single pick still uses a button prompt (`draft_pick`), but Captain 2's two-pick turn is now **one message with a Discord multi-select** (`draft_pick_multi`, `MessageComponentTypes.STRING_SELECT` with `min_values = max_values = 2`) instead of two sequential single-pick prompts — Captain 2 picks both teammates in one interaction, auto-submitting once 2 are selected. `expectedPickCount(turnCaptain, remainingCount)` derives the pick count from how many players are actually left rather than hardcoding it, so an in-flight legacy draft (deployed mid-Captain-B's-turn under the old two-message flow, with 1 of the 2 picks already made) still resolves correctly through the old single-pick path when only 1 player remains. The multi-pick claim (`processDraftPickMulti`) does one atomic `.in("player_id", ids).is("team", null)` update for both selections at once; if a race leaves only some of the selected rows claimed, the partial claim is explicitly reverted (`team` set back to `null` on the ones that succeeded) rather than left half-assigned, and the captain is told to retry.
  - **Fixed this session**: the draft-pick prompt's per-player MMR line now runs the player's raw `mmr` through `getDisplayMMR()` (`mmr_scale`/`mmr_shift`) before display, matching every other MMR-facing surface — it previously showed the raw, unscaled value.
  - **Added this session**: after a captain's pick claim succeeds (both the single-pick and the two-pick multi-select paths), the bot DMs that captain a best-effort confirmation ("You picked **\<name\>**." / "You picked **\<name1\>, \<name2\>**."), reusing the same `is_test_data` guard `sendDraftPickPrompt` already uses (a synthetic test captain has no real Discord account to DM).
- **Balanced mode**: no draft interaction — the bot computes the optimal 3v3 split immediately once the vote resolves and posts the teams-formed summary in the queue channel.
- **Fixed this session**: the "Teams formed!" summary now `@mention`s all 6 players in the message's top-level `content` (not just inside the embed) so Discord actually delivers a notification — embed-only mentions render visually but never notify, the same distinction CLAUDE.md's "Queue channels" section already notes for the first-join role ping.

- `/help` — public, lists available commands. Shows an additional "Admin commands" section only to callers who currently have admin access (see "Admin roles" below), since those commands would just error out for anyone else.
  - **"Thinking..." forever for admin callers, fixed a later session** (`web/lib/discord/adminCommands.ts`): reported live — `/help` deferred (Discord's "thinking..." indicator) and never resolved, for an admin/owner caller specifically. Root cause: `processHelp` built one combined array (public lines + admin lines) and sent it through a single `editOriginalResponse` PATCH — for an admin caller the combined content was 2290 characters, over Discord's 2000-char message-content limit, so the PATCH was rejected by Discord. `editOriginalResponse` (`rest.ts`) only `console.error`s a failed response and never throws or otherwise surfaces the failure to its caller, so the deferred state was never resolved from the end user's side — a non-admin caller never hit this, since the public-only content (1204 chars) stayed under the limit, which is why the bug looked caller-dependent. **Fixed** by splitting the admin-only lines into their own message, sent via the existing `sendFollowupMessage` helper (`rest.ts`) after the first message succeeds — same two-message precedent `/admin config get` already uses for its own listing (see "Admin toolset" above).

### Admin roles (implemented, Phase 2)
- Replaces the single `mod_role_id` config value (superseded — see "Config values" below) with an owner-managed multi-role system: any number of Discord roles can be granted admin access, not just one.

This makes "only the owner can use admin commands until a role is granted" fall out naturally with no special-casing, since the table starts empty.
- Admin-role holders get both (a) the ability to run admin commands and (b) visibility into all match categories/channels (see "Match channels" above).

### Pop-to-report flow
6th join (via `/q`/`/queue`) triggers pop → bot cross-removes those 6 players from the other queue's status message → creates two voice channels in the admin-specified 6-mans call category (one per team, with permission overwrites restricting each team to their own channel) → **if `series_length_vote_enabled`, posts the Best of 3/5/7 vote first and PATCH-edits it into the step below once resolved** → posts vote message with buttons in the queue channel (or auto-resolves via `/vote-default` prefs) → team formation runs (draft via DM-driven picks, Captain 2's two picks collapsed into one multi-select prompt, with queue-channel fallback if DMs are closed; or balanced split) → bot @-mentions all 6 players in the "Teams formed!" message → any participant runs `/report result:<win|loss>` in the queue channel or anywhere (no channel inference, uses `/report result:win` or `/report result:loss` instead) → match result posted to the admin-specified report channel (not the queue channel) → MMR updates (Rank Queue only, scaled by the series-length K-factor multiplier if that vote ran) → band-change DMs fire if applicable → voice channels deleted instantly → all 6 unlocked to queue again. At any point before report, `/cancel` (4-of-6 vote) or `/abandon` (3-of-5 targeted vote) can void the series instead.

## Leaderboard design (Phase 1)

Read-only, public, no auth. Three boards. A player only appears on any board once they've played at least 1 game (any queue).

### 1. Main Leaderboard (Rank)
- Single table showing every player with >=1 game played (placed or not) — sorted by MMR alone, with **no band priority**: a lower-band player above a higher-band player on raw MMR always ranks higher, since band is not itself a ranking dimension. The only grouping is placed vs. unplaced (`is_placed = false` players always sort after every placed player, regardless of either side's band), then MMR breaks every tie within and across bands. This is Rank Queue standing only — Universal Queue never affects MMR, so it doesn't factor into this board's ranking. **Revised this session** (`web/components/UnifiedLeaderboard.tsx`) — supersedes the original band-first-then-MMR comparator: caught via a live leaderboard example where a Garnet player at 847 MMR displayed above an Iron player at 862 MMR, purely because Garnet outranks Iron in `BAND_ORDER` — explicitly not wanted ("All player bands are treated the same, mmr is priority, the only separation is between unbanded and banded players"). `compareLeaderboardRank` now diffs on `is_placed` first (not `bandRank`), then MMR, then player id; `bandRank`/`BAND_ORDER` (`web/lib/leaderboard/stats.ts`) are unchanged and still used elsewhere (Info page, MMR distribution panel, the bot's own promotion/demotion logic) — only the leaderboard's row-ordering stopped consulting them. An earlier fix this same section used to document (games-played tiebreak removed in favor of MMR-then-id) is subsumed by this change, since band is no longer part of the comparison at all.
- Columns: position, player name, band, current MMR, wins, losses, win rate, **last season rank**. Unplaced players show their real, unscaled-transform MMR (not "NA") with band rendered as Unranked — corrected this session; an earlier draft of this doc claimed "NA" for both, which never matched the actual UI (revised this session — no separate "In Placement" section; originally spec'd as a split-out list, superseded in favor of one unified table).
- **Prism players highlighted gold** (revised this session — supersedes the old position-based preview): driven directly by the `is_prism` flag now written live by `recomputeBands()` (see "Bands / ranks"), not a raw top-N-by-row-position calculation — `LeaderboardTable`'s `topCount` prop was removed in favor of a `MainBoardRow.isPrism` field, and the row's icon/label also swap to Prism (`DisplayBand = Band | "Prism"`, `web/lib/leaderboard/rankIcon.ts`) rather than showing the player's real underlying band while highlighted gold.
- **Last season rank**: the player's exact overall numeric standing at previous-season close (e.g. "#23"), based on final MMR ordering among all season participants. Shows **NA** if they played 9 or fewer games last season. Governed by a new config value `season_rank_display_min_games = 10`, kept separate from `top10_min_games = 8` (different thresholds for different purposes — this display cutoff vs. Prism-role eligibility).
- **Paginated**, 20 players per page, with a ‹ / number-input / › stepper at the bottom to move between pages (a range slider until 2026-08-31 — see the season-browser section).
- **🔥 streak flame** (added this session, Main leaderboard only — not Season Stats or All-Time Stats): a player currently on a 3+ game Rank Queue win streak gets a 🔥 rendered next to their name, mirroring the same `FLAME_THRESHOLD` the bot's mention-decoration and streak-bonus logic already use (see "Win-streak bonus" above). `FLAME_THRESHOLD` lives in `web/lib/leaderboard/stats.ts` (not `web/lib/discord/streaks.ts`, which is `server-only` and can't be imported into the client-side leaderboard components) and is re-exported from `streaks.ts` for `report.ts`'s existing import.

### 2. Season Stats Leaderboard
- Scope: current season by default, with a toggle to previous season (if one exists — only current + one prior, no deeper history for v1).
- **Queue-scope filter**: three-way toggle — All Queues / Rank only / Universal only — recomputes every stat column for the selected scope.
- Columns (sortable, so this board doubles as "most games played" / "best win rate" / etc. via column sort rather than separate pages): games played, wins, losses, win rate, longest win streak (that season, that scope), current streak.

### 3. All-Time Stats Leaderboard
- Same shape as the Season board (same queue-scope filter, same sortable columns) but lifetime totals instead of season-scoped. Longest win streak = all-time best; current streak = the same live current streak, still queue-scoped by the filter.
- **Peak MMR** (added this session, per direct user request — "add an all time peak variable for the all-time stats", then "this would only show up for Rank"): a running high-water mark of each player's raw MMR, shown as a "Peak" column. **Only visible on the All-Time board with the Rank queue-filter selected** (`mode === "all-time" && queueFilter === "rank"`, `web/components/StatsBoard.tsx`) — never on the Season board (no per-season peak is tracked, only a lifetime one) and never under the "All"/"Universal" queue-filter options (Universal Queue never moves MMR — see "Queueing" — so a Universal-scoped peak would be meaningless). Reuses the board's existing three-way queue-filter segmented control rather than adding new UI; the column simply isn't there under the other two filter states, including the default "All" view on first load.
  - **Implemented** (`players.peak_mmr`, migration `0031_peak_mmr.sql`): a persisted column, not derived from game history — `CompletedGame` (`web/lib/leaderboard/queries.ts`) has no MMR field, so a true peak can't be reconstructed after the fact and has to be maintained imperatively going forward, the same way `total_games_played`/`rank_games_played`/`band_games_played` are already running counters rather than recomputed from history. Backfilled to `greatest(mmr, 0)` for existing rows at migration time — a truthful lower bound, since MMR starts at 0 and only ever rises above a player's current value at the same write sites this feature hooks into, so "at least their current MMR, floored at 0" cannot overstate any player's real historical peak.
  - **Bumped via `Math.max(p.peak_mmr, newMmr)` at all three MMR-increasing write sites**: `report.ts`'s Rank Queue settle block, `adminTools.ts`'s `processCorrectReport` (`/admin correct-report`), and `adminTools.ts`'s `processAdjustMmr` (`/admin adjust-mmr`) — the last one included even though it's an ungated admin override with no Rank Queue restriction, so peak stays consistent with current MMR (`peak_mmr >= mmr` always holds) regardless of how MMR got raised, not just through normal reports. **`processCorrectReport`'s piece of this was later revised to sometimes lower instead — see "Corrections can now LOWER a stale peak" below.**
  - **Not tracked while unranked, fixed a later session**: all three bump sites above now gate the bump on `p.is_placed` (`peak_mmr: p.is_placed ? Math.max(p.peak_mmr, newMmr) : p.peak_mmr`) — an unplaced player's MMR is still swinging around during placement games (provisional K, no real band yet), so it isn't a meaningful "peak," and showing one made an `Unranked`/`NA`-band player look like they had a real ranked history on the All-Time board. **Seeded at the moment of actual placement instead**: `recomputeBands()` (`bands.ts`) already flips `is_placed` from `false` to `true` for a newly-placed player in its per-player update — that same write now also sets `peak_mmr: Math.max(player.peak_mmr, player.mmr)` (only for `action === "placed"`, a `{}` spread no-op otherwise), so a fresh placement's peak starts at whatever MMR they actually placed with rather than staying at 0 until their next reported game bumps it. Without this seed, `peak_mmr >= mmr` could transiently break right after placement (peak still 0, mmr already their real placement-game value) until a later game happened to be a win.
  - **Never lowered by the two MMR-decreasing write sites** — `seasonClose.ts`'s `applyMmrDecay` (season soft-reset, mathematically only ever shrinks MMR's magnitude toward 0) and `adminTools.ts`'s `processUnreport` (reverses a report by subtracting the stored delta) — both left untouched. Since neither can push `mmr` above the already-stored `peak_mmr`, the `peak_mmr >= mmr` invariant survives with no code needed at either site; this is also consistent with this file's existing precedent for admin corrections not fully unwinding every derived side effect (e.g. `grace_inactivity_days`/`last_rank_game_at` similarly isn't rewound by `/admin unreport`).
  - **`/admin reset`** (full game-data wipe, keeps player records) resets `peak_mmr: 0` alongside `mmr: 0` and the other stat counters, since peak is itself a stat being reset to a clean slate. **`/admin full-reset`** needs no equivalent change — it deletes player rows outright rather than zeroing their stats.
  - **Test-data generator** (`web/lib/test-data/generate.ts`): synthetic players from the `/dev` panel set `peak_mmr: Math.max(spec.mmr ?? 0, 0)` alongside their seeded `mmr` at insert time — without this, a freshly-seeded test player (whose `mmr` is set directly, never through the incrementing write sites above) would show a peak of 0 next to a current MMR as high as 950, which is exactly the kind of visibly-broken state this column exists to avoid, and would be the first thing visible when eyeballing this feature via the dev panel. **Revised alongside the "not tracked while unranked" fix above**: an unplaced synthetic player (`totalGames < PLACEMENT_GAMES_REQUIRED`) now seeds `peak_mmr: 0` instead, matching the same rule real players follow.
  - **Home-page All-Time tab showed `NA` for everyone, fixed a later session** (`web/components/UnifiedLeaderboard.tsx`): the All-Time Stats board exists at two entry points — the standalone `/stats/all-time` route and a client-side tab on `/` (`UnifiedLeaderboard`), both rendering the same `StatsBoard`. `StatsPlayer.peakMmr` was declared **optional**, and `UnifiedLeaderboard`'s `statsPlayers` map omitted it, so every row on the home-page tab got `undefined`, which `StatsBoard`'s `p.peakMmr ?? 0` fallback turned into `0` — indistinguishable from a genuine "no peak yet" and therefore rendered as `NA` for all players. `/stats/all-time` passed the field and was correct throughout, which is exactly what made this present as a caching/deployment problem and cost a long misdiagnosis (browser cache, service workers, stale Vercel aliases, PostgREST schema cache, and the Supabase anon key were all investigated and cleared before the actual two-call-sites-one-component structure was noticed). **Fixed** by making `peakMmr` **required** on `StatsPlayer` and dropping the `?? 0` fallback, so a producer that forgets it is a compile error rather than a plausible-looking zero; all three producers (`app/stats/all-time/page.tsx`, `app/stats/season/page.tsx`, `UnifiedLeaderboard`) now pass `player.peak_mmr`. **Lesson worth keeping**: an optional prop plus a numeric default silently converts "field missing" into "field is zero" — for a field whose zero value is itself meaningful (here, "unranked, no peak"), that collapses a wiring bug into a legitimate-looking data state.
  - Rendered with the same `applyMMRTransform(mmr, scale, shift)`/`Math.round(...)` display convention every other MMR-facing surface uses (`web/components/UnifiedLeaderboard.tsx`'s established pattern) — `StatsBoard.tsx` already had this helper function and its `mmrScale`/`mmrShift` props defined but unused before this feature, apparently pre-staged for exactly this.
  - **Corrective backfill for stale `peak_mmr` values, added a later session** (`web/scripts/backfill-peak-mmr.ts`): reported live — many placed players showed `peak_mmr = 0` despite having real positive-MMR history, which the user correctly flagged as implausible by chance now that Elo deltas are asymmetric (team-strength-weighted, skew factor, min-delta floor) rather than a simple zero-sum split — landing back at exactly 0 essentially never happens organically. Root cause: migration `0031_peak_mmr.sql`'s backfill (`peak_mmr = greatest(mmr, 0)`) only captured each player's **current** mmr at the single moment that migration happened to run, not their true historical high — anyone whose mmr had already come back down by then (a losing streak, season decay, an admin correction) got a `peak_mmr` permanently floored at that low/negative snapshot, with no code path to retroactively correct it (the `is_placed`-gated write-site bumps and the placement-time seed, both described above, only ever raise `peak_mmr` going forward from new events — neither revisits a player's past). **Fix**: rather than re-deriving a second, parallel history-replay implementation, this script reuses `web/lib/mmr/reconstructMmrHistory.ts` as-is (the same module `backfill-mmr-before.ts` already relies on for `series_players.mmr_before`) — extended with a `peakMmrByPlayer` output tracked alongside the existing mmr replay: a running high-water mark per player, started (seeded from their mmr at that exact instant, not any earlier pre-placement high) the moment their simulated `rankGamesPlayed` first crosses `placementGamesRequired` — mirroring `bands.ts`'s real placement-time seed — and only raised thereafter by later series deltas or admin adjust-mmr overrides, exactly matching the live `is_placed`-gated bump semantics; decay events are never checked since both decay formula pieces are non-increasing in magnitude and so can never set a new high. Unit-tested (`reconstructMmrHistory.test.ts`) for the placement-instant seed (not the earlier pre-placement high), continuing to rise on later gains, staying put through later losses, and the admin-adjustment-before-vs-after-placement distinction. The script (`npm run backfill-peak-mmr`, same dry-run-by-default/`--write` convention as `backfill-mmr-before`) only ever **raises** a currently-placed player's `peak_mmr` — `Math.max(existing peak_mmr, reconstructed peak, current mmr, 0)` — never lowers one, and leaves unplaced players' `peak_mmr` untouched (correctly 0 while unranked). Like its sibling script, not yet run against the live database from this sandbox (no Supabase credentials here) — verified only via the pure function's own `vitest` suite and `tsc --noEmit`; running it for real is left to the user.
  - **Corrections can now LOWER a stale peak, added a later session** (user's prompt: *"how does correcting a match work in terms of accounting for their peak mmr because a player could have gotten their peak from a miss report"*): the backfill script above only ever raises `peak_mmr`, by design — every write site does. But a correction is exactly the one moment a stored peak can be *provably* wrong: if a misreported win was itself what pushed a player to a new peak, correcting that report back to a loss should retroactively lower the peak it created, not leave it permanently stuck via `Math.max`. **New shared module** `web/lib/mmr/peakMmrRecompute.ts` (`recomputeTruePeakMmr(supabase)`): the query-building half of `backfill-peak-mmr.ts` (paged/chunked players, seasons, reported non-test series, series_players, `adjust_mmr` audit-log rows parsed via the same `"MMR: <before> -> <after>"` details format, season_history checkpoints) was extracted out of the script and into this module so both the offline script and the two live correction paths share one implementation instead of duplicating query logic; `backfill-peak-mmr.ts`'s `main()` now just calls it and keeps its own only-ever-raises write loop unchanged. Deliberately has **no `"server-only"` import** (same reasoning as `reconstructMmrHistory.ts`/`seasonDecay.ts`) so both a tsx script and a Next.js route handler can import it directly. **Full player population is required even though only a handful of players' peaks are ever in question**: `reconstructMmrHistory`'s season-close decay step computes its median over every currently-placed, non-test player (mirroring `applyMmrDecay`'s real query — see "Seasons" above), not just whichever players a caller cares about, so scoping the replay to only the corrected players would silently corrupt that median for anyone who's lived through a season close in between. **Cheap guard to avoid a full replay on every correction**: `adminTools.ts`'s `processCorrectReport` (`/admin correct-report`) and `correct.ts`'s `applyCorrection` (`/correct`) each compute every affected player's corrected MMR into a `Map` first, then only flag a player as a peak-recompute candidate if they're currently `is_placed` **and** their corrected MMR has dropped below their currently-stored `peak_mmr` — i.e. only when the stored peak might plausibly have been set by the very result now being corrected. `recomputeTruePeakMmr()` (loaded via dynamic `import()`, so it isn't pulled in on corrections with no candidates) runs at most once per correction, covering every candidate in that one replay. For a flagged candidate, the reconstructed value is written directly — `Math.max(reconstructed, correctedMmr, 0)`, still floored at 0 and at the player's own new MMR, but **no longer floored by the old stale `peak_mmr`** — while every non-candidate keeps the ordinary `p.is_placed ? Math.max(p.peak_mmr, correctedMmr) : p.peak_mmr` write every other site uses. No new migration — pure application logic over the existing `mmr`/`peak_mmr` columns.

## Match time stats (analytics page)

Tracks when matches get played — not for gameplay purposes, purely an analytics curiosity, added this session per direct user request. Three graphs: a per-30-minute-segment time-of-day breakdown (overall / Supercharged / non-Supercharged), a per-day-of-week breakdown (overall only), and an MMR distribution histogram with live scale/shift preview sliders (added a later session — see below).

- **"Supercharged day" = the existing Weekly Bonus Day mechanic** (`series.bonus_day_multiplier > 1` — see "Weekly bonus day" above). Confirmed by re-reading `bonusDay.ts`'s Pacific-time day-of-week logic before building this, rather than inventing a second, separate concept.
- **No raw timestamps stored** — the user explicitly asked for an increment-only counter model for memory efficiency ("we will just increment values... this makes it so data is just increased, not created"), not a per-match log. `crl6mansqueuebot_time_of_day_stats` (migration `0025_match_time_stats.sql`) is a fixed 48-row table, one row per 30-minute Pacific-time segment of the day (`segment_index` 0..47, 0 = 00:00–00:29), with `supercharged_count`/`non_supercharged_count` columns; `crl6mansqueuebot_day_of_week_stats` is a fixed 7-row table (`day_of_week` 0..6, Sun=0..Sat=6, matching `bonusDay.ts`'s existing convention), single `count` column. Both tables are seeded with all their rows up front (`generate_series`) — a match never inserts a new row, only increments an existing one. The "overall" line on the time-of-day graph is derived at read time (`supercharged_count + non_supercharged_count`) rather than stored as a third redundant counter.
- **Increment point**: once per real (non-test-data) match, at team-formation time — not once per player, and not at report time (a match's time-of-day is when it started, not when it happened to be reported). Hooked into `teamFormation.ts`'s `finalizeTeams` (the single function every formation path — balanced split, both captains-draft completion paths — already funnels through for `teams_formed_at`/private-match-credentials), via `recordMatchTimeStats()` (`web/lib/discord/matchTimeStats.ts`), which computes the Pacific-time segment index and day-of-week index from `new Date()` at that moment and calls a single atomic RPC (`crl6mansqueuebot_increment_match_time_stats`, does both table updates in one round-trip) so a concurrent report/formation race can't cause a lost update. Both queue types are tracked (not Rank-only) — a Universal match still has a real time-of-day, it just always lands in the non-Supercharged bucket since Bonus Day only ever applies to Rank Queue. Best-effort: wrapped in try/catch, since a stats-counter failure must never block match creation. Test-data matches are excluded, same as every other stats feature.
- **Access**: a normal `Match Times` nav link next to `Info` in the top nav (`web/app/layout.tsx`) — **revised this session**, supersedes the original easter-egg design below. The route still has no auth gate, same as `/info`. **Superseded design**: originally reached only by typing the exact string `CW62751` (case-insensitive) into the player-search box (`web/components/SearchBar.tsx`) as a `router.push()` side effect instead of running normal player-name matching — removed this session, along with the `HIDDEN_PAGE_TRIGGER`/`HIDDEN_PAGE_ROUTE` constants and the now-unused `useRouter` import in `SearchBar.tsx`, once the page became a discoverable nav link instead.
- **Page** (`web/app/match-times/page.tsx`): mirrors `/info`'s exact back-link/heading/`.panel` structure (`force-dynamic`, `← Back to Leaderboard` link, `.panel animate-in-delay-*` wrappers) per explicit request ("a back button at the top just like the info page"). Reads both tables via `getMatchTimeStats()` (`web/lib/leaderboard/queries.ts`) and renders two `LineChart` instances.
- **`LineChart`** (`web/components/LineChart.tsx`): a hand-rolled SVG line chart, not a charting library — this project has no charting dependency installed and has consistently avoided adding npm dependencies beyond the bare minimum (see "Website implementation notes" below). Takes pre-aggregated `series`/`xLabels` and plots them on a shared 0..max y-axis; purely presentational, no data-fetching or business logic of its own.
- **MMR distribution graph + preview sliders** (added a later session, per direct user request): a third panel on the same hidden page, showing a histogram of current Rank Queue player MMR plus aggregate stats (total/rank/universal matches played, player count, average/median/min/max MMR, and a per-band+Prism+Unranked player-count breakdown) and two range sliders that preview `mmr_scale`/`mmr_shift` without writing anything.
  - **`BarChart`** (`web/components/BarChart.tsx`): a second hand-rolled SVG chart, mirroring `LineChart.tsx`'s exact padding/viewBox/grid-line conventions — same minimal-dependency precedent, purely presentational (`bars: {label, value}[]` in, nothing else).

Match counts use `select("*", { count: "exact", head: true })` rather than fetching and counting rows — CLAUDE.md's `seasonClose.ts` note (see "Seasons") already documents that PostgREST silently truncates unbounded selects past a project row cap with no error, which a naive `.length` count would walk straight into.

The per-band+Prism+Unranked counts intentionally use the wider eligible set instead, since Unranked players are honestly part of that breakdown.

This is what keeps the bars visually fixed (correct/expected) while the numbers around them respond to the sliders, rather than the whole chart appearing to reshuffle on every drag.

That was a real bug, not just an approximation: since the bonus range is admin-mutable, changing it later silently reclassified every already-elapsed day, not just future ones — caught when the user changed the range and the reported "N supercharged / M non-supercharged" split changed retroactively for days that had already happened under the old range. **Fixed** (`web/lib/discord/bonusDay.ts`): two new `crl6mansqueuebot_config` counters, `match_time_stats_supercharged_days`/`match_time_stats_nonsupercharged_days`, are incremented **once per Pacific calendar day**, at the moment that day ends, classified against whatever the bonus config says **right then** — never revisited afterward. `match_time_stats_last_marked_date` (a plain `YYYY-MM-DD` Pacific date string) tracks the last day already counted, so a day is counted exactly once regardless of how many times the check runs. `computeDayAdvanceSteps(lastMarkedDate, today, bonusDayEnabled, bonusDayStart, bonusDayEnd)` is the pure, unit-tested function (`bonusDay.test.ts`) that turns a gap into one step per fully-elapsed day (today itself excluded, since it hasn't finished); `advanceMatchTimeStatsDayCounters(now)` is the thin DB-backed wrapper that reads/writes the three config keys. Wired into the per-minute sweep (`web/app/api/discord/sweep/route.ts`, new best-effort/non-fatal block, same precedent as every other check in that route) rather than a separate cron — a no-op on nearly every tick (a Pacific day only rolls over once every ~1440 ticks) and self-catches-up multiple days at once if the sweep was ever down across a day boundary, evaluating each caught-up day against the config available *now* (still an accepted approximation for a multi-day gap specifically, since there's no historical config log to consult for the exact days in between — but no longer an approximation for the ordinary case of a single day ending under whatever config was active at the time). `computeDayTrackingTotals()` (used by the Day of Week panel) is unaffected and unchanged, since its denominator was never actually config-dependent. Migration `0040_match_time_stats_day_counters.sql` seeds the two counters from the exact same real history `0038` already established (7 days, 2026-08-08 through 2026-08-14 Pacific, 1 supercharged/6 non-supercharged) and sets `match_time_stats_last_marked_date` to `2026-08-14`, so the switch to daily counting picks up from 2026-08-15 onward with no gap or double-count. **Needs manual production application**, same as every other recent migration.

## Mafia mini-game

`/mafia` — a standalone party-game command, unrelated to queueing/MMR/bands. Per direct spec: someone runs it, an embed opens with Join/Leave buttons and waits for 6 players (the host auto-counts as the first), 5 grace seconds once full, then one of the 6 is privately, randomly told they're the Mafia and everyone else is told they're Innocent; a 2-minute countdown auto-cancels the lobby if it never fills.

- **Fully independent of `crl6mansqueuebot_players`** — deliberate design choice, not an oversight: this is a party game any server member can join regardless of whether they've ever queued, so it has no business touching MMR/band/placement state or requiring a player row to exist. `crl6mansqueuebot_mafia_games`/`crl6mansqueuebot_mafia_players` (migration `0035_mafia.sql`) store only raw Discord ids, display names, and (for players) the interaction token captured at join time — no join to the main player table anywhere in `web/lib/discord/mafia.ts`.
- **One lobby per channel while open**: a partial unique index (`crl6mansqueuebot_mafia_games_active_channel_idx`, on `channel_id` where `status in ('waiting','starting')`) rejects a second `/mafia` run in the same channel while one's already in flight (Postgres error `23505`, caught in `processMafiaCommand` and turned into a friendly ephemeral reply) — mirrors the "existence = pending" convention this codebase already uses elsewhere (`series_lobby`, `sub_requests`) rather than a status check-then-insert race.
- **Join/leave concurrency**: `crl6mansqueuebot_mafia_join`/`crl6mansqueuebot_mafia_leave` (same migration) are advisory-lock-guarded plpgsql RPCs (`pg_advisory_xact_lock(hashtext(game_id))`) mirroring `crl6mansqueuebot_join_queue`/`leave_queue` from `0002_queue_system.sql` — the same atomic-pool-of-N pattern, just keyed by game id instead of queue type. The join RPC atomically flips `status` from `'waiting'` to `'starting'` the instant the 6th player is inserted, **inside the same advisory-lock transaction as the insert** — this means only the one join call that actually observed the count reach 6 is ever responsible for driving the grace-then-reveal sequence, eliminating a double-start race by construction rather than needing a separate claim step afterward. Leave is restricted to `status='waiting'` only (rejected once the lobby is `'starting'`/`'started'`/`'cancelled'`), so there's no race between a last-second leave and an in-flight 5-second grace countdown. The host's own "starts at 1" join is just an ordinary call to the same join RPC made right after the game row is created — no special-casing needed.
- **Ephemeral role reveal via stored interaction tokens** (`web/lib/discord/mafia.ts`'s `runMafiaFinalizeSequence`, using `sendFollowupMessage` from `rest.ts`): there is no bot-token REST call that can send an arbitrary ephemeral message to a user out of band — only a response/followup tied to the interaction token that originally created it works, and that token has a 15-minute window. Each player's `interaction.token` (from their Join button click, or from the host's original `/mafia` invocation) is persisted at join time specifically so it can be reused later, once the lobby fills, to deliver a genuinely private role message — the lobby's whole lifecycle (up to `mafia_timeout_seconds` to fill, plus `mafia_grace_seconds`) is comfortably inside that window.
- **Four embed states**, one lobby message PATCH-edited through each (`mafiaWaitingEmbed`/`mafiaStartingEmbed`/`mafiaStartedEmbed`/`mafiaCancelledEmbed` in `mafia.ts`, same single-message-edited-through-states pattern `teamFormation.ts` already uses for its vote/draft/teams-formed message): **Waiting** (`BRAND_COLOR`, roster + Join/Leave buttons, footer states the timeout), **Starting** (`AMBER_COLOR`, buttons removed, "Starting in N seconds..." once the 6th player joins), **Started** (`GOLD_COLOR`, buttons removed, roster shown — the actual role assignments are never posted here, only delivered privately), **Cancelled** (`RICH_LEAVE_COLOR`, either "Everyone left" or "Not enough players joined in time" / a crash-backstop message, depending on cause).
- **Empty-lobby edge case**: if every player (including the host) leaves before reaching 6, `processMafiaLeave` sees `player_count === 0` and immediately, atomically claims `status: 'waiting' → 'cancelled'`, posting a quiet "Everyone left — lobby cancelled." embed — rather than leaving a 0-player `waiting` row blocking the channel's unique-active-lobby index for up to `mafia_timeout_seconds` until the sweep would otherwise catch it.
- **2-minute auto-cancel** (`mafia_timeout_seconds`, config default 120): implemented in the per-minute sweep (`web/app/api/discord/sweep/route.ts`), since it exceeds a single interaction's safe background-execution window — queries `status='waiting'` lobbies older than the timeout, atomically claims each to `'cancelled'`, then calls `cancelStaleMafiaLobby` (exported from `mafia.ts`) to post the "Not enough players joined in time — lobby cancelled." embed. A second, defensive block in the same sweep tick targets lobbies stuck in `'starting'` for more than 10 minutes — a crash-safety backstop (mirroring this route's existing orphaned-voice-channel cleanup precedent) for the case where the invocation running the 5-second grace-then-reveal sequence got killed mid-flight, which would otherwise leave the lobby permanently blocking its channel's unique-active-lobby index with no player-facing recourse. Both blocks feed one shared `mafiaLobbiesCancelled` counter in the sweep's JSON summary.
- **Config**: `mafia_grace_seconds` (default 5) and `mafia_timeout_seconds` (default 120), both in `KNOWN_CONFIG_DEFAULTS` (`config.ts`) and `register-commands.mjs`'s `CONFIG_KEYS` — unlike `bonus_day_*`/`streak_bonus_enabled`, these have no dedicated subcommand and are settable through the generic `/admin config set`, since there was no strong reason (bounds-checking, Discord-native choice list) to warrant a bespoke command the way those others did.
- **Button styles/colors**: Join is `SUCCESS` (green), Leave is `DANGER` (red) — otherwise unthemed, since this feature has no brand precedent to match (unlike queue/vote buttons).
- `/mafia [password:]` is a mostly-no-option command (`register-commands.mjs`), listed in `/help`'s public command section (`adminCommands.ts`) — no admin gate, anyone can run it.
- **Optional lobby password, added a later session** (migration `0036_mafia_password.sql`, `crl6mansqueuebot_mafia_games.password text null`): the host can set `/mafia password:<text>` at creation time (trimmed; empty/whitespace-only is treated as no password) to gate the lobby — any player clicking **Join** on a password-protected lobby must enter the same password before their join is even attempted. The waiting embed shows a 🔒 in the title and a "password-protected" line whenever `game.password` is set, so players know before clicking.
  - **Modal-based UX** (`web/lib/discord/mafia.ts`, `web/lib/discord/types.ts`, `web/app/api/discord/interactions/route.ts`) — the first modal usage anywhere in this codebase: `handleMafiaJoinButton` became `async` and now does a cheap pre-check (`select("status, password")`) before deciding how to respond — a password-protected, still-`'waiting'` lobby gets a Discord **Modal** response (`InteractionResponseType.MODAL`, a single `INPUT_TEXT` field) instead of the usual deferred-update-then-background-process flow; every other case (no password, already full/started/cancelled) falls through to the existing `after(() => processMafiaJoin(...))` path unchanged. Submitting the modal delivers a **new**, separate interaction (`MODAL_SUBMIT`, same `custom_id` prefix `mafia_join_modal:`) — dispatched by a new branch in `route.ts` (this route previously handled `PING`/`MESSAGE_COMPONENT`/`APPLICATION_COMMAND` only) to `handleMafiaJoinModalSubmit`, which extracts the typed password via a new `modalFieldValue(interaction, customId)` helper (`types.ts`, walks `data.components`'s nested `ACTION_ROW`/`INPUT_TEXT` tree — a shape this codebase's `DiscordInteraction` type had never needed to represent before) and defers into the same `processMafiaJoin`, now accepting an optional `submittedPassword` param it checks (trimmed) against `game.password` before calling the join RPC at all — a mismatch replies "Incorrect password." and never touches `crl6mansqueuebot_mafia_players`.
  - **Plaintext storage, deliberate**: `password` has no column-level access restriction on a table whose RLS policy is `for select using (true)` — same accepted tradeoff this file already documents for `crl6mansqueuebot_series.private_match_password` (`0024_private_match_credentials.sql`): a low-stakes lobby access code, not a real credential, so it isn't worth the extra column-GRANT/REVOKE machinery.
  - **Latent bug fixed in the same pass**: `processMafiaJoin`/`processMafiaLeave` both run via `after()` scheduling, i.e. *after* their triggering button click already got a synchronous `DEFERRED_UPDATE_MESSAGE` ack from `route.ts` — every ephemeral error reply in those two functions was going through a `callbackError` helper that POSTed to the interaction's one-shot `/callback` endpoint a second time, which Discord silently rejects once an interaction's already been acknowledged (of any type). Every "Couldn't identify you" / "already in this lobby" / "lobby is full" / etc. error was therefore never actually reaching the player. Replaced with `replyError` (`sendFollowupMessage(interaction.token, ...)`, matching the working pattern `runMafiaFinalizeSequence`'s role-reveal delivery already used) — works correctly regardless of the interaction's initial ack type, since it goes through the webhook token rather than the one-shot callback.
- Migrations `0035_mafia.sql` and `0036_mafia_password.sql` still need to be applied to the production Supabase project manually, same as every other recent migration (this sandbox has no DB write access).
- **`crl6mansqueuebot_mafia_join`/`crl6mansqueuebot_mafia_leave` ambiguous-column bug, fixed a later session** (migration `0043_fix_mafia_join_rpc.sql` — numbered `0043` rather than the next-available `0037` at the time it was written, since a separate concurrent session had already claimed `0037`-`0042` for unrelated work by the time this was committed): `0035`'s table DDL applied cleanly to production (the `/mafia` embed posted fine with Join/Leave buttons), but every RPC call failed with Postgres error `42702` ("column reference \"status\" is ambiguous") — reported live as the host never appearing in the roster ("nobody yet") and every Join click failing with "Something went wrong joining." Root cause: `returns table (status text, player_count int)` implicitly declares `status` as a PL/pgSQL variable inside the function body, which collides with the `crl6mansqueuebot_mafia_games.status` column referenced by the bare `select status into v_status from crl6mansqueuebot_mafia_games where id = p_game_id` line in both functions — a genuine bug present in `0035` from the start, not a partial-migration artifact. **Fixed** by qualifying the column reference (`select crl6mansqueuebot_mafia_games.status into v_status from ...`); the `update ... set status = 'starting'` line elsewhere in `crl6mansqueuebot_mafia_join` was never ambiguous, since an `UPDATE`'s `SET` left-hand side is unambiguously the target column. `0043` re-creates both functions via `create or replace function` (idempotent, safe to re-run) plus their grants — **needs manual production application, same as every other migration from this sandbox.**

A `pagerMovedRef` flag (set only by the pager's own controls, and only when the page actually changes) keeps it from fighting the search highlight's own `scrollIntoView`.
- **Match History's pager got the same treatment** (2026-08-31, `HistoryBoard.tsx`): its `type="range"` slider — the last one left on a board — became the identical "Page ‹ [n] › of N" stepper, with the same typed draft, clamp-on-commit, `field-invalid-flash`, `playTap()` on the arrows, and end-of-document snap scroll (the pager is the last thing on `/history` too, and a 12-card page grid shortens the same way a 20-row table does). Its `pagerMovedRef` additionally keeps the snap from firing when `selectPlayer()` resets to page 1 on a filter change, which would otherwise yank the viewport to the bottom of a board the reader just re-filtered; that path also resets `pageInputDraft` to "1". The remaining `type="range"` inputs in the codebase are the Match Times MMR scale/shift preview sliders, which are genuinely continuous and stay sliders.
- `<LeaderboardTable key={isCurrentSeason ? "live" : selectedSeasonNumber}>` — the remount resets the table's internal `page` and search highlight; without it, stepping from page 3 of the live board into a shorter season renders a blank page with no explanation.
- **Band is archived per season** (added 2026-08-31, migration `0049_season_history_band.sql`): `crl6mansqueuebot_season_history.band_at_close text null check (band_at_close in ('Iron','Garnet','Emerald','Sapphire'))`, written by `seasonClose.ts`'s `historyRows` as `r.player.is_placed ? r.player.band : null` — read before `resetAllPlacementsToUnranked()` clears it, same as the `is_prism`/`is_placed` snapshots beside it. Without it every past-season row rendered **Unranked**, since the soft reset wipes `band` for the whole roster. Snapshotted rather than derived from `mmr_at_close`: band cutoffs are admin-tunable percentile config (the live server runs 20/50/80, not the code default 40/70/90), so deriving would silently rewrite past seasons whenever they changed. Holds the **underlying** band, never `"Prism"` — Prism stays the `made_top10` overlay both boards already apply on top. Consumed by `historicalMainBoardRows`, `historicalTopPlayersRows` **and** the Hall of Fame (all changed together; leaving any one on the live band would make the season views disagree about the same player in the same season). In `hallOfFame.ts` the band is now a parameter threaded through `buildSlots`/`toHofPlayer` instead of being read off `player.band`: closed seasons pass a map built from `band_at_close`, the active season passes the live column unchanged. Only the **games** and **streak** slots actually show it — a top-3 slot's band icon is already replaced by the Prism icon via `inTopThree` (`HallOfFameSlotCard`), which is why the bug was invisible on the podium and visible only on the other two cards. Null = unplaced at close, and also = written before the migration — indistinguishable, but vacuous: `season_history` was empty when it landed. **Migrations 0048 (`season_score`) and 0049 (`band_at_close`) must both be applied to production Supabase before the next `/newseason`**, and they only help seasons closed *after* they land. PostgREST rejects a write naming a column the table doesn't have (PGRST204) rather than dropping the field, so closing a season against an un-migrated table archives nothing.

- **Season-history write is now guarded** (added 2026-08-31, `seasonClose.ts`): the standings upsert destructures `error` and throws `Failed to archive season standings: …`. It was previously a bare `await supabase.from(…).upsert(rowsChunk)`, and supabase-js *resolves* on a failed write rather than throwing — so a rejected upsert was completely silent and `closeSeason` carried straight on into `applyMmrDecay()` + `resetAllPlacementsToUnranked()`, destroying the standings it had just failed to record. The PGRST204 path above made that reachable in practice, not just theoretically. Throwing aborts **before** anything destructive runs; the caller's atomic claim has already flipped `is_active=false` on the season row, but MMR and placements are untouched, so the standings stay fully derivable from live data — apply the migration, then reopen/close. Both callers already catch: `processNewSeason` replies "Failed to create the new season — check logs", and the sweep's scheduled-reset block logs `Sweep: scheduled season reset failed` (note it deletes `scheduled_season_reset_at` *before* running, so an aborted scheduled reset does not retry itself — pre-existing behavior for any failure there). This is the only write in the file.
- **Not yet exercised against real data**: no season has closed on the live server (`seasons` = 1 active row, `season_history` = 0 rows), so today the picker is pinned to Season 1 and only the live branch renders. When the first season closes, sanity-check that each row's `wins + losses` equals its archived `season_games_played`; if it doesn't, test series are leaking in, because `getAllPlayersWithGames()` does not filter `is_test_data` on series while `seasonClose.ts` does. That gap is pre-existing and equally affects the live board's lifetime W/L.
